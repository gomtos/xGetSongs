# Tauri 사이드카 스파이크 보고서

작성일: 2026-10-10
설계: [2026-10-10-tauri-kotlin-sidecar-design.md](2026-10-10-tauri-kotlin-sidecar-design.md)
계획: [2026-10-10-tauri-sidecar-spike.md](../plans/2026-10-10-tauri-sidecar-spike.md)

환경: Windows 11 Home 10.0.26200, JBR 21.0.9(`java`), Rust 1.99.0, Tauri 2, WebView2 154.0.4258.62, Kotlin 2.4.20 / Ktor 3.6.0. 측정은 같은 PC에서 `shell.exe`(`--config spike.conf.json`으로 만든 릴리스 빌드)를 직접 실행해서 했고, 값은 셸이 남긴 결과 파일(`spike-ready.json`, `spike-record.txt`, `spike-job.txt`)과 프로세스 목록에서 스크립트로 읽었다. 앱 데이터 폴더는 `%TEMP%\xgs-spike-appdata`이고 사용자의 `%APPDATA%\xGetSongs`는 건드리지 않았다.

## 필수 관문

| 번호 | 조건 | 결과 | 근거 (측정값, 걸린 시간) |
|---|---|---|---|
| M1 | 신호를 읽고 Rust에서 `/tools` 200 | **통과** | 3회 모두 화면이 Rust의 `/tools` 호출 성공 뒤에만 남기는 `toolsMs`가 기록됐다(393, 393, 374ms). 시작 신호 해석, 토큰 헤더 호출이 동작한다 |
| M2 | 창 닫기 → 3초 안에 java 없음 | **통과** | 984, 884, 928ms 만에 셸과 사이드카가 모두 없어졌다. 3회 모두 남은 사이드카 0 |
| M3 | 강제 종료 → 5초 안에 java와 yt-dlp 없음 | **통과** | 영상 하나의 조회 중 701ms 만에 `yt-dlp.exe`가 보였고 부모는 사이드카 `java.exe`였다. 셸을 `Stop-Process -Force`로 끝내자 **166ms** 만에 사이드카, `yt-dlp`, 셸이 모두 사라졌고 2초 뒤에도 0이었다. 사이드카 자신의 정상 종료(stdin 닫기)는 약 0.7초가 걸리고 그것으로는 자손(`yt-dlp`)이 정리되지 않으므로, 이 결과는 Job Object가 한 일이다 |
| M4 | 웹뷰 직접 fetch가 막힘 | **통과** | 웹뷰(WebView2)가 토큰 헤더를 달아 서버를 직접 `fetch`하면 3회 모두 `blocked: TypeError: Failed to fetch`. 같은 요청에 `Origin: http://tauri.localhost`를 달아 `curl`로 보내면 `403`이다. `Guard.kt`는 바꾸지 않았고, Rust 브리지(`http_get`)로는 `Origin` 없이 200이 온다 |

## 악화 한도와 기록

동기가 UI 품질이므로 개선이 아니라 나빠지지 않는 선만 본다(설계 §5.1).

|---|---|---|---|
| waitedMs (3회, 중앙값) | 1,945ms (1,945 / 1,968 / 1,925) | 10초 이하 | **통과** |
| readyMs (3회, 중앙값) | 1,405ms (셸이 사이드카를 띄운 때 → 시작 신호) | 기록만 | |

해석할 때 조심할 점:

- 창이 뜬 뒤 사이드카가 준비될 때까지 사용자가 보는 시간은 약 2초(`waitedMs`)이고, 창 자체는 0.13초 만에 뜬다. 한도(10초)에는 한참 못 미치지만 그 2초 동안 화면이 비어 있다는 점은 1~2단계에서 "시작 중" 표시로 다룰 일이다.
- `waitedMs`는 화면 스크립트가 시작된 뒤부터 재므로 웹뷰를 만드는 시간은 들어 있지 않다. 셸 프로세스를 시작한 때부터 준비까지는 대략 2초다(창이 0.13초 만에 뜨고 사이드카가 그 직후 약 1.4초 만에 준비되므로).
- Compose 앱과 사이드카의 시작 시간은 같은 구간을 재지 않았으므로 직접 비교하지 않는다. 같은 PC에서 파일 캐시가 데워진 뒤의 값이다(콜드 스타트는 재지 않았다).
- 크기는 JRE를 넣지 않았다. 사이드카 lib + 셸 = 81.2MB, Compose 업 jar = 108.5MB로 차이는 약 27MB(Compose/Skia 쪽)다. JavaFX 웹뷰(34.3MB)는 양쪽에 그대로 들어 있고, 사이드카 lib에는 쓸 데 없는 Linux용 Netty 네이티브 jar도 몇 MB 들어 있다. JRE 번들 크기는 5단계에서 jpackage로 잰다.

## 막힌 점과 고친 것

- **계획의 설계 결함 하나를 실제 프로세스 확인에서 찾아 고쳤다.** 사이드카가 시작 신호를 쓴 뒤 `main`이 끝나면, 서버(Ktor Netty)의 스레드도 부모 감시 스레드도 모두 데몬이라 JVM이 종료를 시작한다. 시작 신호 약 125ms 뒤에 포트가 닫히고 약 1.6초 뒤에 코드 0으로 끝났다. 단위 테스트는 테스트 JVM이 계속 살아 있어서 이를 못 잡았다. 실제 프로세스를 띄워 시작 신호 3초 뒤에도 `/tools`가 200인지 보는 `SidecarProcessTest`를 먼저 실패시키고(처음 만든 버전은 종료가 진행 중인 프로세스를 보고 통과해서 3초 대기와 HTTP 확인으로 강화했다), `runSidecar`가 감시 스레드를 돌려주고 `main`이 그것을 `join`하게 고쳤다. 계획서 Task 3은 실제 코드에 맞게 고쳤다.
- 스파이크 화면은 0a의 UI 프로토타입(`index.html`, `main.ts`)을 덮어쓰지 않고 `spike.html`로 따로 두고, 스파이크 빌드만 `spike.conf.json`으로 그 페이지를 열게 했다. 셸이 측정값을 파일로 남기게 해서 측정을 화면 읽기 없이 스크립트로 했다. M3는 큰 재생목록 대신 영상 하나의 조회(`yt-dlp -J`)로 했다. 계획서 Task 6과 7은 이에 맞게 고쳤다.
- Vite 8은 `build.rollupOptions.input`을 경고 없이 받았다. `tsc`, `cargo check`, 빌드 모두 첫 시도에 통과했다.
- 그 밖의 계획과 다른 점은 없다.

## 판정

**통과.** M1~M4가 모두 통과했고 `waitedMs`(약 1.9초)가 한도(10초) 안이다. 다음으로 쓸 계획서는 설계 §5의 1단계 "사이드카 완성"이다. 거기서 다룰 것:

- `Diagnostics`(로그 파일, 종료 기록, `last-run.txt`, UI 멈춤 감시)를 `app`에서 옮기거나 사이드카에 맞게 바꾼다. 지금 사이드카는 stderr 로그만 쓴다.
- 번들한 JRE로 실행한다(`java`를 환경 변수가 아니라 번들 경로로).
- 사이드카 lib를 줄인다(Linux용 Netty 네이티브 jar 등).
- 시작 중의 2초를 화면에서 어떻게 보일지(2~3단계).

이 스파이크가 확인하지 않은 것: JRE를 번들했을 때의 시작 시간과 크기, 콜드 스타트, 실제 다운로드 작업 중의 종료(취소와 정리), Windows Defender나 SmartScreen의 반응, 셸이 이미 다른 Job 안에서 시작된 경우(터미널이나 런처가 Job을 쓰는 경우)의 동작이다. 이 PC에서는 PowerShell에서 직접 실행한 경우만 확인했다.
