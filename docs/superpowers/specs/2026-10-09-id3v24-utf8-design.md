# ID3 태그를 ID3v2.4 + UTF-8로 쓰기

작성일 2026-10-09. 작업 메모의 "id3tag 인코딩을 utf로 변경"을 다룬다.

## 목표

받은 mp3의 ID3 텍스트(제목, 가수, 앨범 아티스트, 앨범, 트랙, 주석, 가사)를 모두 UTF-8로 쓴다. UTF-8은 ID3v2.4부터 있는 인코딩이므로 태그 버전을 v2.3에서 v2.4로 올린다.

## 지금 상태

- 엔진은 ffmpeg로 `-id3v2_version 3` 태그를 쓴다. ffmpeg는 한글처럼 ASCII가 아닌 값은 UTF-16(인코딩 바이트 1), ASCII뿐인 값은 ISO-8859-1(0)로 쓴다.
- ffmpeg가 만들지 못하는 COMM(주석)과 USLT(가사) 프레임은 `Id3Frames`가 ffmpeg 출력 뒤에 직접 이어 붙인다. 이 코드는 v2.3 전용이다(프레임 크기는 일반 빅엔디언, 다른 버전은 거부). COMM은 ASCII뿐이면 ISO-8859-1, 아니면 UTF-16이고 USLT는 항상 UTF-16이다.

## ffmpeg로 확인한 사실

같은 입력(한글 제목, 영문 가수, `Café` 앨범)을 `-id3v2_version 3`과 `4`로 썼을 때:

| 버전 | TIT2(한글) | TPE1(영문) | TALB(`Café`) |
|---|---|---|---|
| v2.3 | 1 (UTF-16) | 0 (ISO-8859-1) | 1 (UTF-16) |
| v2.4 | 3 (UTF-8) | 3 (UTF-8) | 3 (UTF-8) |

v2.4에서는 영문뿐인 값도 UTF-8이고, 헤더 플래그는 0이다.

## 설계

### `FfmpegCommands.tag`

`-id3v2_version`의 값을 `4`로 바꾸고 KDoc의 "ID3v2.3"을 "ID3v2.4"로 고친다.

### `Id3Frames`

- **버전:** 기존 태그는 v2.4만 받는다. v2.3과 v2.2는 지금처럼 `unsupported ID3 tag layout`으로 거부한다. ffmpeg가 이제 항상 v2.4를 쓰므로 v2.3을 받을 이유가 없다. 태그가 없는 파일에 만드는 새 헤더는 버전 바이트가 4다.
- **헤더 플래그:** v2.4의 플래그 바이트는 `%abcd0000`이다(a 비동기화, b 확장 헤더, c experimental, d footer). experimental(0x20)만 레이아웃을 바꾸지 않으므로 그대로 통과시키고, 비동기화(0x80), 확장 헤더(0x40), footer(0x10), 정의되지 않은 하위 4비트(0x0F)가 하나라도 있으면 거부한다.
- **프레임 크기:** v2.4는 프레임 크기가 syncsafe(바이트당 7비트)다. 읽을 때(`endOfFrames`)와 새 프레임을 쓸 때 모두 syncsafe로 처리한다. 크기 바이트에 0x80 이상이 있으면 "프레임 크기가 syncsafe가 아니다"라는 오류로 거부하고, 새 프레임의 본문이 syncsafe 한도(0x0FFFFFFF)를 넘으면 `IOException`이다.
- **COMM:** 인코딩 바이트 3, 언어 `eng`, 빈 설명(종결자 `00` 한 바이트), 본문은 UTF-8이다. BOM은 없다. 영문뿐인 값도 UTF-8로 쓴다(ffmpeg의 v2.4 출력과 같다).
- **USLT:** 인코딩 바이트 3, 언어(한글이 있으면 `kor`, 아니면 `eng`), 빈 설명(`00`), 본문은 UTF-8이다. 줄바꿈은 지금처럼 CRLF이고 이미 있는 CRLF는 겹치지 않는다. 언어 판별은 그대로다.
- 파일 재작성 절차(임시 파일, 교체, 정리, 실패 시 원본 유지)와 "COMM·USLT가 둘 다 비면 파일을 열지도 않는다"는 규칙은 바뀌지 않는다.

### 이미 받은 파일

다시 태그하지 않는다. 앞으로 받는 파일부터 v2.4 + UTF-8이다.

## 테스트

- `FfmpegCommandsTest`: 기대하는 명령줄의 `"-id3v2_version", "3"` 두 곳을 `"4"`로 바꾼다.
- 테스트 도구:
  - `testutil/Id3v2Tag.kt`: 버전이 4이면 프레임 크기를 syncsafe로 읽고, COMM·USLT 디코딩이 인코딩 3(UTF-8)을 알게 한다(0과 1도 그대로 읽는다).
  - `testutil/Fakes.fakeTaggedMp3()`: v2.4 헤더(`ID3` + 버전 4)로 바꾼다. 프레임 크기 `6`은 syncsafe로도 같은 바이트다.
- `Id3FramesTest`:
  - 헬퍼(`tagged`, `frame`, 새 헤더 기대값)를 v2.4로 바꾼다. 프레임 크기는 syncsafe다.
  - COMM·USLT 기대 바이트를 UTF-8(인코딩 3)로 바꾼다: ASCII 주석, 한글, BMP 밖 문자(이모지, 4바이트), BOM 없음, 가사 CRLF·언어 판별.
  - UTF-16 전용 테스트(BOM, 서로게이트 쌍)는 UTF-8 테스트로 바꾸고, "프레임 크기는 일반 빅엔디언"은 "syncsafe이고 128을 넘는 크기가 7비트 경계를 건넌다"로 바꾼다.
  - 미지원 버전 케이스를 v2.4에서 v2.3과 v2.2로 뒤집고, 헤더 플래그 거부 테스트에 footer(0x10)를 더하며 하위 비트 케이스는 4비트(0x0F) 기준으로 바꾼다. 프레임 크기가 syncsafe가 아닌 깨진 태그도 거부하는지 본다.
- `Id3TaggerTest`: "엔진은 v2.3만 확장한다"는 케이스의 거부용 헤더를 v2.4에서 v2.3으로 뒤집는다.
- `RealFfmpegTaggingIntegrationTest`(실제 ffmpeg):
  - 태그 버전이 4이고 한글 제목(TIT2)이 인코딩 3인지 확인한다(`theTagIsId3v2Point3WithUtf16Text…`의 이름과 단정을 고친다).
  - 영문 가수(TPE1)도 인코딩 3인지 확인한다. 이것이 "ISO-8859-1이 남지 않는다"는 증거다.
  - COMM과 USLT의 기대 인코딩을 3으로 바꾸고, ffprobe가 한글 제목·주석·가사를 같은 값으로 읽는지는 지금 검증을 유지한다.
  - 입력 mp3를 만드는 `-id3v2_version 3`도 `4`로, 헬퍼 이름(`silentMp3WithAV23Tag`)도 맞게 바꾼다.

## 문서

- 설계 문서 `2026-10-04-xgetsongs-design.md` §6.4: "ID3v2.3을 쓴다(… UTF-16 … ISO-8859-1로 ffmpeg가 정한다)"를 "ID3v2.4를 쓰고 모든 텍스트는 UTF-8"로, 값 항목의 "UTF-16으로 쓰고 줄바꿈은 CRLF"를 "UTF-8로 쓰고"로 고친다.
- `README.md` "ID3 태그": "ID3v2.3 태그"를 "ID3v2.4 태그(텍스트는 UTF-8)"로 고친다.
- 지난 계획서(`docs/superpowers/plans/`)는 이력이므로 고치지 않는다.

## 위험

- v2.4를 읽지 못하는 아주 오래된 플레이어나 차량 오디오는 태그를 못 보여 줄 수 있다. 요즘 Windows 탐색기와 주요 플레이어는 읽는다. 구현 뒤 새로 받은 mp3를 사용자가 쓰는 플레이어에서 한 번 확인한다.
- 이미 받은 v2.3 파일과 새 v2.4 파일이 섞인다.
