# Tauri Rust 브리지(2단계) 보고서

작성일: 2026-10-11
설계: [2026-10-10-tauri-kotlin-sidecar-design.md](2026-10-10-tauri-kotlin-sidecar-design.md) §5의 2단계

환경: Windows 11 Home 10.0.26200, Rust 1.99.0, Tauri 2.12, 사이드카 이미지는 1단계의 `server\build\sidecar-image`(JBR 21.0.9). 측정은 `npm run tauri build -- --no-bundle --config check.conf.json`으로 만든 릴리스 `shell.exe`를 직접 실행해서 했고, 실행마다 새 임시 폴더를 앱 데이터와 로그 폴더로 썼다. 사용자의 `%APPDATA%\xGetSongs`는 건드리지 않았다. 서버와 Kotlin 코드는 바꾸지 않았다.

## 측정

| 항목 | 이번 단계 (3회) | 1단계 |
|---|---|---|
| 창이 뜬 뒤 사이드카가 준비될 때까지 `waitedMs` | 1,033 / 975 / 973ms (중앙값 975) | 중앙값 1,952ms |
| 점검 페이지 명령 왕복 최악 `worstPingMs` | 8 / 11 / 12ms | — |
| 프레임 간격 최악 `worstFrameGapMs` | 60 / 45 / 48ms | — |
| 이벤트 5,000개 (`Channel`) | 289 / 283 / 291ms, 유실 0, 역전 0 | — |
| 명령이 끝났을 때 이미 받은 이벤트 수 | 5,000 / 5,000 / 5,000 | — |
| 창 닫기 → 셸과 사이드카 모두 없음 | 1,073 / 972 / 977ms | 861 / 845 / 844ms |
| 시작 직후 닫기 → 모두 없음 (창이 생기자마자) | 2,764 / 2,766 / 2,680ms, 남은 사이드카 0, 마커 `reason=user` | — |
| 셸 강제 종료 → 사이드카 없음 | 156 / 146 / 145ms | 324ms |
| `shell.exe` | 4.4MB | 4.4MB |

해석:

- `waitedMs`가 1단계의 절반인 것은 사이드카를 `run()`의 맨 앞에서, 창과 웹뷰를 만들기 전에 띄우기 때문이다. 시작부터 준비까지의 총 시간은 같은 JVM이라 비슷하고, 창이 뜬 뒤에 기다리는 몫이 줄었다.
- 창 닫기가 1단계보다 100~200ms 길다. 이번에는 닫는 순간 점검 페이지가 방금 끝난 직후이고 `Lifecycle`의 잠금과 대기를 거치는 경로가 더해졌다. 한도(3초)에 한참 못 미쳐서 원인을 더 파지 않았다.
- 이벤트 5,000개가 명령이 끝나기 전에 모두 도착했으므로, 이 PC에서는 "명령은 끝났는데 마지막 이벤트를 아직 처리하지 못한" 경우를 보지 못했다. 그래도 `watchJob`은 `job-done`이 실제로 전달될 때까지 기다리게 만들어 두었고(3초 안에 오지 않으면 오류), 이것은 `bridge.test.ts`가 지킨다.
- 시작 직후 닫기는 창이 사라진 뒤 사이드카가 뜨기를 기다렸다가 `exit` 줄로 정상 종료하므로 약 2.7초 걸리고, 마커가 `reason=user`로 남는다. 이전에는 이 경우를 Job Object가 죽여서 다음 시작이 크래시 경고를 낼 수 있었다.

## 막힌 점과 고친 것

- 계획을 쓰며 스크래치에서 같은 확인을 한 번 돌렸을 때 확인용 스크립트의 결함 두 가지를 찾아 계획에 반영했다. 실행에서는 다시 나타나지 않았다.
  - 프로세스를 띄운 지 40ms쯤에 잡히는 `MainWindowHandle`은 닫기를 받지 않는 창이라, 그 핸들로 `CloseMainWindow()`를 부르면 셸과 사이드카가 그대로 남는다. 도우미가 제목이 생긴 창을 기다린다(`Wait-CheckWindow`).
  - 토큰 검색의 대조 문자열 길이가 44여서 검색이 아무것도 찾지 못했다. 대조 문자열을 코드로 만든 43자로 바꿨다.
- 점검 페이지의 `tools` 키 순서는 서버의 순서가 아니라 알파벳순(`ffmpeg,jsRuntime,ytDlp`)이다. `serde_json::Value`가 객체의 키를 정렬해서 두기 때문이고 JSON 객체에서는 의미가 없다. 확인 스크립트의 기대값을 그에 맞췄다.
- 계획의 `BAD_JOB_ID` 문서 주석이 없는 함수 이름(`valid_job_id`)을 가리켜서 실제 이름(`check_job_id`)으로 고쳤다.
- 그 밖의 Task 1~7은 계획대로 첫 시도에서 각 RED/GREEN 개수가 계획과 같았다.

## 리뷰 뒤 고친 것

전체 변경분을 새 문맥의 리뷰어(Opus)가 읽고 "고치면 병합 가능"으로 판정했다. Critical은 없었고 Important 둘을 고쳤다.

- **`watchJob`의 리스너가 예외를 던지면 그 뒤의 이벤트가 영원히 오지 않았다.** Tauri의 `Channel`은 핸들러가 던지면 번호를 올리지 않아 이후 메시지를 모두 쌓아 두기만 한다(리뷰어가 실제 `@tauri-apps/api`로 재현). 화면의 작은 버그 하나가 진행률 전체를 말없이 멈추고 "이벤트를 모두 받지 못했습니다."라는 엉뚱한 문구를 띄웠을 것이다. 이제 래퍼가 리스너의 예외를 `console.error`로 알리고 다음 이벤트를 계속 전달한다. 테스트 `a listener that throws does not stop the events that come after it`을 먼저 실패시킨 뒤 고쳤다(화면 쪽 19개).
- **이 보고서의 B3가 실제보다 많이 주장했다.** 점검 페이지는 `install_yt_dlp`와 `update_yt_dlp`를 부르지 않았는데 "명령 8개 통과"라고 썼다. `update_yt_dlp`는 yt-dlp가 없으면 내려받지 않고 바로 실패하므로, 점검 페이지와 실제 사이드카 계약 테스트에 더했다(둘 다 서버의 `yt-dlp가 설치되어 있지 않습니다.`를 받는다). 점검 페이지가 바뀌어 셸을 다시 만들어 3번 돌렸고 13개 항목이 모두 PASS다(`waitedMs` 1,023 / 1,060 / 1,050ms, 명령 왕복 최악 4 / 13 / 23ms, 프레임 간격 최악 61 / 53 / 57ms, 이벤트 5,000개 329 / 320 / 313ms, 창 닫기 735 / 776 / 826ms, 토큰 모양 문자열 0건). `install_yt_dlp`는 여전히 웹뷰에서 확인하지 않았다.

리뷰어가 Minor로 낸 것은 고치지 않고 아래 "3단계 이후로 넘기는 것"에 적었다.

## 정정 뒤의 실제 조회·다운로드 확인

사용자가 시험할 주소(자신의 재생목록 중 한 곡이 `v=`인 주소)를 주어서, 위의 정정대로 임시 앱 데이터의 `bin`에 앱의 yt-dlp 복사본을 두고 실제 사이드카 이미지로 `sidecar-host/tests/real_download.rs`(`#[ignore]`, 환경 변수 `XGS_SIDECAR_DIR`·`XGS_REAL_YTDLP`·`XGS_REAL_URL`)를 두 번 돌렸다. 재생목록 전체는 받지 않는다: 조회(메타데이터)만 하고 그 영상 한 곡만 받으며, 두 번째 작업은 첫 진행률 이벤트에서 바로 취소한다. 원본 yt-dlp와 사용자의 앱 데이터는 건드리지 않았고 임시 폴더는 지웠다.

| 확인 | 결과 (두 번 모두 통과) |
|---|---|
| `GET /tools` | yt-dlp 2026.08.19, ffmpeg, JS 런타임을 찾음 |
| `POST /resolve` (재생목록 주소) | 항목 101개, 모두 사용 가능, `truncated=false`, `alsoVideoId`가 `v=`와 같음, 3.5초 |
| `POST /jobs` (`ranks`로 한 곡) + `GET /jobs/{id}/events` | 이벤트 13개 5.5초와 12.1초(첫 이벤트 `item-started`, 진행률 9개가 100까지, `item-done`, 마지막 `job-done` `COMPLETED`, 성공 1), 3,005,360바이트 `.m4a` 한 개 |
| 이벤트의 필드 | 모든 이벤트의 필드가 `types.ts`의 `JobEvent`와 정확히 같음(서버가 null 필드도 씀) |
| `DELETE /jobs/{id}` (진행 중 취소) | `job-done` `CANCELLED`가 취소 호출 뒤 229ms와 188ms에 옴, 이어진 두 번째 취소는 "작업을 찾을 수 없습니다.", 시험 뒤 `yt-dlp`·`ffmpeg`·사이드카 프로세스 0개 |

이것은 3곡짜리 작업의 취소다. 2026-10-09에 사용자가 보고한 101곡 다운로드 중 취소가 멈춘 현상(재현에 실패해 코드 변경 없이 열려 있는 문제)을 재현하지는 않았다.

## 판정

**통과.** 웹뷰가 `invoke`와 `Channel`만으로 서버의 기능을 쓰고(`install_yt_dlp`만 실제 호출을 확인하지 못했다), 포트와 토큰은 `sidecar-host`의 `Bridge` 안에만 있다. 가짜 서버로 시험한 계약 75개와 실제 사이드카 계약 1개, 화면 쪽 19개가 통과했다. 다음은 설계 §5의 3단계 "프런트엔드 이식"이다.

## 이 단계가 확인하지 않은 것

- 실제 조회와 다운로드. (정정: 처음에는 "yt-dlp가 이 PC에 없다"고 썼으나 틀렸다. 사용자의 앱이 `%APPDATA%\xGetSongs\bin\yt-dlp.exe`에 설치한 yt-dlp가 있다. 이 단계의 모든 확인은 실행마다 새 임시 앱 데이터 폴더를 써서 사용자의 폴더를 건드리지 않았고, 서버는 앱 데이터의 `bin`을 먼저 찾은 뒤 PATH를 보는데 그 임시 폴더에는 yt-dlp가 없고 PATH에도 없어서 `found=false`였을 뿐이다. 임시 폴더에 그 파일의 복사본을 두면 실제 조회·다운로드도 시험할 수 있었으나 하지 않았다.) 사용자가 주소를 주어서 이 항목은 아래 "정정 뒤의 실제 조회·다운로드 확인"에서 `Bridge`와 실제 사이드카, 실제 yt-dlp로 확인했다. 남은 것은 그 실제 이벤트가 웹뷰의 `Channel`과 화면 코드까지 가는 구간뿐이다(`Channel`의 순서와 속도는 점검 페이지의 5,000개 이벤트가 보였고, 실제 이벤트의 필드는 `types.ts`와 같음을 아래에서 확인했다). 3단계의 첫 화면 연결에서 눈으로 확인한다.
- 사이드카가 실행 중에 죽는 경우. 그 뒤의 호출은 `서버와의 연결이 끊어졌습니다.`를 받고 다시 시작하지 않는다(화면이 안내하고 앱을 다시 시작하게 할지는 3~4단계에서 정한다).
- Job Object를 만들었는지는 아무 데도 기록하지 않는다(스파이크의 `spike-job.txt`를 없앴다). 4단계에서 셸의 로그와 함께 다룬다. 강제 종료 시 자손(`yt-dlp.exe`)이 함께 정리되는지는 임시 앱 데이터에 yt-dlp가 없어 실제 자손이 없는 상태로만 확인했고(위 정정 참고), Job Object 코드는 바꾸지 않았다.
- 점검 페이지(`check.html`)와 점검용 명령 3개(`check_record`, `check_ping`, `check_burst`)는 개발자용으로 남아 있다. 6단계에서 지울지 정한다.
- `install_yt_dlp`: 파일을 내려받는 호출이라 웹뷰에서도 실제 서버에도 부르지 않았다. 요청 형식은 가짜 서버 테스트가 지키고, 실제 호출은 3단계의 첫 설치 때 확인한다.

## 3단계 이후로 넘기는 것

리뷰어의 Minor와 권고다. 고치지 않았다.

- **새로고침으로 돌고 있는 작업을 이어 볼 수 없다**(3단계 전에 정할 것). 릴리스 빌드에서도 F5와 Ctrl+R이 동작하고, 서버는 작업의 이벤트를 한 번만 받게 해(`JobRegistry.claim`) 새로고침한 페이지가 `이미 다른 곳에서 이 작업의 이벤트를 받고 있습니다.`를 받는다. 가속키를 끄거나 복구를 설계한다. `watchJob`이 거절된 뒤에 늦게 오는 이벤트도 여전히 `onEvent`로 가므로 무시할지 정한다.
- **셸에 로거를 붙일 때(4단계) `ureq`의 debug 로그가 `X-XGS-Token`을 그대로 찍는다**(`Authorization`과 `Cookie`만 가려진다). `ureq` 대상은 Info 이상으로 거른다. 지금은 로그 백엔드가 없어서 새지 않는다.
- 시작이 `STOP_START_WAIT`(10초)보다 오래 걸리는데 사용자가 창을 닫으면, 셸은 `RunEvent::Exit` 콜백이 끝나자마자 프로세스를 끝내므로 사이드카는 Job Object가 죽이고 다음 시작이 크래시 경고를 낸다. 정상 종료 약속은 시작이 10초 안에 끝나는 경우에만 지켜진다.
- `LISTENER_GONE`은 사실상 일어나지 않는다. Tauri 2.12의 `Channel::send`는 페이지가 새로고침되거나 사라져도 `Ok`를 돌려주므로, 옛 스트림이 `job-done`까지 blocking 스레드 하나를 붙잡는다.
- 60초 제한에 걸린 짧은 호출(과 UTF-8이 아닌 본문)도 `서버와의 연결이 끊어졌습니다.`로 보고된다. `start_job`이 시간 초과로 실패해도 서버는 작업을 만들었을 수 있어서 다시 시도하면 작업이 둘이 될 수 있다.
- 사이드카 시작 실패의 사유가 영어로 사용자에게 간다(`서버를 시작하지 못했습니다: the sidecar did not say it was ready within 60 s`). 짝 없는 서로게이트가 든 문자열 인자는 명령에 닿기 전에 영어 오류로 거절된다(`toWellFormed()`로 피할 수 있다).
- 실제 사이드카 테스트는 토큰을 로그 폴더에서만 찾고 `data\sidecar-stderr.log`는 보지 않는다(이번 수동 검색은 이 파일까지 덮었다).
- 이월: `sidecar-stderr.log`는 여전히 크기 제한이 없다, 로그 폴더가 있는데 쓸 수 없는 경우의 폴백이 없다, 프로토타입의 `탐색기에서 보기`는 실행 중 비활성이다, TypeScript 모델(`types.ts`)이 `ApiModels.kt`와 같은지는 손으로 지킨다(3단계에서 계약 테스트나 생성으로 바꿀지 정한다).
