## 1. 질문과 전제

이 저장소에는 Python 코드가 없다. 지금은 Kotlin 백엔드(`shared`, `engine`, `server`, `diagnostics`)에 Tauri 셸(Rust `sidecar-host` + `shell`의 TypeScript)을 얹은 구조다. 이 문서의 "Python 이행"은 **Kotlin 백엔드를 Python으로 다시 쓰고 PyInstaller나 Nuitka로 exe 하나를 만드는 것**을 뜻한다. 다른 뜻이면 이 문서의 전제부터 고친다.

## 2. 장점

1. **구조 단순화(가장 큰 이득).** 백엔드와 UI를 Python 한 프로세스(pywebview + WebView2)로 합치면 사이드카를 다루는 코드가 필요 없어진다: `sidecar-host`(Rust 약 3,000줄), `XGS-READY` 핸드셰이크, stdin 종료 신호, `ParentWatch`, Job Object, 그리고 `Guard`의 Origin·토큰 때문에 둔 Rust 브리지(설계 §2.2). 단 **Tauri를 버릴 때만** 얻는다. Tauri를 유지하면 이 이득은 없다.
2. **진짜 파일 하나.** PyInstaller `--onefile`은 exe 자체가 번들이라 5단계의 `resources` 미내장과 가상 파일 시스템 문제가 사라진다. ffmpeg, yt-dlp, Node는 지금처럼 외부에 남는다.
3. **크기.** 159MB가 수십 MB대로 줄 것으로 **추정**한다(측정하지 않음). 크기는 비목표라 판단에는 크게 쓰지 않는다.
4. **yt-dlp와 같은 언어.** `import yt_dlp`로 진행률 훅과 메타데이터 dict를 직접 받으면 stdout 파싱(`ProgressParser`, `ErrorClassifier`, `VideoInfoFile`, `--progress-template`)이 줄어든다. 단 §3의 5, 4번 때문에 이 이득은 실제로는 작아질 수 있다.
5. **Kotlin을 고수할 이유 하나가 이미 사라졌다.** 원래 `shared`를 Wasm 웹에서 재사용하려고 KMP를 골랐지만(설계 §10.3), 3단계에서 `js(IR)` 타깃을 만들지 않고 TS로 포팅했다.

## 3. 단점과 위험

1. **재작성 비용과 회귀 위험.** 이 프로젝트의 가치는 코드보다 테스트에 있다(테스트가 코드의 약 2.5배). 제목 파싱 픽스처, 예약어, LRCLIB 매칭 같은 엣지 케이스가 거기 있다. 완화책은 3단계에서 이미 쓴 방식이다: 같은 이름의 테스트로 포팅하고, Kotlin 구현과 같은 무작위 입력으로 대조하는 도구(커밋 `45fb1a1`)를 Python용으로도 만든다.
2. **글자 수 세는 방식 차이(확인한 함정).** `FilenameFormatter.kt`의 길이 제한(`text.length`, `substring`, 100~103행)은 UTF-16 단위이고 서로게이트 쌍을 쪼개지 않게 보호한다. TS 포트도 UTF-16 단위라 일치한다(`shell/src/logic/filename.ts` 115행의 주석). Python `len()`은 코드포인트라서 이모지(설계 §6.2 픽스처의 🎤)나 보충 평면 문자가 든 제목은 180자·80자 한계의 위치가 달라진다. 파일명이 달라지면 "기존 파일 건너뛰기·덮어쓰기" 판단도 이전에 받은 파일과 어긋난다. UTF-16 단위로 세는 헬퍼를 명시해야 한다. 반면 `shared`는 정규식이 아니라 수작업 파서라(`\p{…}`와 `RegexOption` 사용 없음) 정규식 이식 문제는 작다. `engine`의 정규식은 확인하지 않았다.
3. **구글 가사 카드(JavaFX WebEngine 숨은 웹뷰)에 Python 대응물이 없다.** `engine/lyrics/google` 패키지는 581줄이고 테스트가 656줄이다. 선택지:
   - pywebview 숨김 창: WebView2를 쓰지만 GUI 메인 스레드를 점유하고, 숨김 창에서의 스크립트 실행과 폴링 동작은 확인하지 않았다.
   - Playwright나 QtWebEngine: Chromium을 번들하므로 크기 이득이 사라진다.
   - 기능 삭제: README가 이미 약관 위반 소지, 마크업 변경 시 조용한 실패, 정식 API(Musixmatch 등) 권고를 적고 있다.

   이 결정이 이행 방식을 사실상 정한다. 현행 7단계도 같은 문제를 WebView2로 푸는 것을 검토 중이다.
4. **취소와 프로세스 트리 정리를 다시 만들어야 한다.** `SystemProcessRunner`는 취소 시 `descendants()`를 모두 종료한다. Rust 쪽 Job Object는 M2/M3 관문(5초 안에 자손 정리)을 통과했다. Python에서는 `psutil`이나 `ctypes`로 새로 구현하고 다시 검증해야 한다. `yt_dlp`를 in-process로 쓰면 취소는 진행 훅에서 예외를 던지는 협조적 방식뿐이라, 취소 안전성만 보면 서브프로세스가 낫다(그러면 §2의 4번 이득이 줄어든다).
5. **yt-dlp 갱신과 충돌한다.** 설계 §8의 전제는 "YouTube 변경으로 자주 깨지니 앱 전용 폴더의 yt-dlp를 갱신한다"이다. exe 안에 얼리면 갱신할 수 없어서 외부 yt-dlp(서브프로세스나 내려받은 zipapp)를 계속 쓰게 된다.
6. **ffmpeg는 뺄 수 없다.** mutagen이 태그는 써도, 조각난 DASH m4a를 일반 M4A로 다시 쓰는 stream copy와 썸네일 JPEG 변환·정사각 크롭은 ffmpeg가 한다(설계 §6.4).
7. **onefile의 품질 문제.** 실행마다 `%TEMP%`에 풀어서 시작이 느려질 수 있고, 백신과 SmartScreen 오탐이 흔한 편이다. 코드 서명은 범위 밖이다(설계 §3). onedir은 단일 파일이 아니고 Nuitka는 빌드가 오래 걸린다. 모두 **측정하지 않았다.**
8. **UI 목적이 보존되는지 미검증.** 0a 관문에서 사용자가 직접 확인한 것은 U1뿐이고, 한글 조합 입력·글꼴·네이티브 느낌(U2~U4)은 "낫다고 간주"한 채 미확인이다. 그래서 "WebView2가 입력과 글꼴을 운영체제 방식대로 처리한다"는 가설은 Tauri 경로에서도 아직 확정되지 않았다. pywebview도 WebView2를 쓰므로 같을 것으로 **가정**하지만, 어느 경로든 한글 조합 입력과 글꼴은 실제 화면에서 직접 확인해야 한다(P6).

## 4. 경로 비교

| 경로 | 내용 | 이득 | 비용 |
|---|---|---|---|
| **A** | 전부 Python + pywebview, 단일 프로세스 | 사이드카·브리지·Rust 소멸, 파일 1개, 크기 감소 | 백엔드 재작성, Tauri 셸 폐기, 가사 웹뷰 재결정, UI 관문 재확인 |
| **B** | Python 사이드카로 JVM만 교체, Tauri 유지 | 159MB 감소. 프로토콜(HTTP + SSE + 토큰 + stdout 핸드셰이크 + stdin 종료)이 언어 중립이라 Rust 변경은 `sidecar-host/src/config.rs`의 java 실행부 정도. 단일 파일 사이드카는 `externalBin` 규칙에 맞는다(설치본에서 exe 옆에 놓일 뿐 파일 하나가 되지는 않는다) | A와 같은 재작성 비용. 사이드카·브리지 복잡성은 그대로. 가사 웹뷰는 Python 사이드카에 GUI가 없어 셸이 맡거나 삭제해야 함 |
| **C** | 현행 완주(5~6단계) | 남은 일이 작다. 필요하면 `jlink`로 런타임 축소(5단계 계획) | 159MB와 SFX 문제를 감수 |

B는 비용이 A와 같은데 이득은 크기뿐이라 가장 애매하다.

## 5. 권고

**지금은 C.** 화면은 이미 TS로 옮겼고(1~4단계 통과) 그 화면은 백엔드 언어와 무관하다. Python 이행은 UI를 개선하지 않는다. 크기와 시작 속도는 비목표인데 재작성 비용은 크다. 다만 UI 품질 가설(U2~U4)이 미확인이라는 점은 어느 경로를 택하든 남는 별개의 일이다(§3의 8번).

## 6. A를 검토할 조건

아래 셋이 모두 확정될 때만 검토한다.

1. "exe 파일 하나"가 필수 요건이다.
2. 구글 가사 폴백을 지워도 된다(또는 정식 API로 바꾼다).
3. Tauri를 포기해도 된다.

## 7. 결정 전에 싸게 확인할 것

**C의 측정:** 5단계(SFX + `jlink`) 결과의 크기, 시작 시간, 백신 반응. 5단계에서 어차피 재는 값이다.

**Python 스파이크(하루):** PyInstaller `--onefile`로 `yt_dlp` + 최소 HTTP 서버를 묶어서 같은 항목을 잰다. 기존 관문(M1~M4)처럼 판정하며, 값은 제안값이고 바꿀 수 있다.

| 번호 | 조건 | 제안 한도 |
|---|---|---|
| P1 | 깨끗한 Windows에서 exe가 뜨고 `GET /tools` 같은 응답이 온다 | 통과 여부 |
| P2 | 콜드 스타트(더블클릭 → 응답 가능) 3회 중앙값 | 현행 `waitedMs` 1.95초보다 크게 나빠지지 않음(10초 이하) |
| P3 | exe 크기 | 기록만 |
| P4 | Windows Defender·SmartScreen이 막거나 경고하는가 | 막으면 중단 |
| P5 | 취소·종료 시 `yt-dlp`와 `ffmpeg` 자손까지 5초 안에 정리되는가 | M3과 같은 조건 |
| P6 | pywebview(WebView2)에서 한글 조합 입력, 붙여넣기, 선택, 우클릭 메뉴가 된다 | 0a의 U2와 같은 조건. 이번에는 "간주"가 아니라 직접 확인 |
| P7 | 숨김 창으로 구글 가사 카드를 읽을 수 있는가 (삭제를 택하면 생략) | 통합 테스트 재검증 |

P4, P5, P6 중 하나라도 실패하면 A는 접는다.

## 8. 확인하지 않은 것

- Python 쪽 크기, 콜드 스타트, 백신 반응은 모두 추정이며 측정하지 않았다.
- 줄 수는 경로로 센 근삿값이고 `engine`의 정규식 사용은 확인하지 않았다.
- pywebview의 숨김 창, 한글 입력, 메인 스레드 제약은 문서와 경험에 근거한 가정이다.
- Nuitka와 PyInstaller 중 무엇이 나은지는 비교하지 않았다.
- 이 문서는 Windows 전용(README의 1단계 범위)을 전제로 한다.
