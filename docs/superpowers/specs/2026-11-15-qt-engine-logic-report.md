환경: Windows 11 Home 10.0.26200, Visual Studio 2022(vcvars64), Qt 6.11.3, 정답 쪽 JVM은 `server/build/sidecar-image`의 OpenJDK 21.0.9와 그 안의 `engine.jar`·`shared-jvm.jar`·`kotlinx-serialization` jar. 창은 띄우지 않았고 네트워크도 쓰지 않았다. Gradle은 돌리지 않았다(사이드카 이미지가 이미 있었고, `run.ps1`의 오래된 오라클 검사가 통과했다).

이 문서의 "관문 표"에 있는 숫자는 Task 8에서 관문 전체를 처음부터 한 번 돌린 결과다(깨끗한 릴리스·디버그 빌드, 두 빌드의 테스트, 두 점검 스크립트, 대조 네 번). 그 밖의 숫자(관찰 표, 변이 시험, Task별 대조 통계)는 각 Task가 자기 작업 중에 돌린 결과이고, 그 자리마다 "Task N의 실행"이라고 적었다. Task 8은 그것들을 다시 돌리지 않았다.

## 요약

- 설계 §4의 Q2a 관문 두 조건(이식 대상 `engine` 테스트 157개가 같은 이름으로 모두 통과, 대조 불일치 0)은 이 PC에서 지금 코드로 돌린 범위에서 **충족됐다.** Q1의 관문(테스트 193개, Q1의 대조 종류)도 같은 실행에서 다시 충족됐다.
- 이식한 것: 오류 분류(`ErrorClassifier`), 진행률 파싱(`ProgressParser`), 영상 정보 파일 읽기(`VideoInfoFile`), yt-dlp·ffmpeg 명령 조립(`YtDlpCommands`, `FfmpegCommands`), 태그 파일 만들기(`TrackTags`, `Ffmetadata`), 동시 다운로드 수(`DownloadConcurrency`), 가사 후보 매칭(`LyricsMatcher`), 그리고 그것들이 쓰는 데이터 형(`ApiModels`의 도메인 형, `ToolPaths`, `LyricsQuery`). 기반으로 `xgs::kt`에 코드 포인트 글자 판정·NFKC·실수 파싱·ASCII 공백 판정을 더했고, `kotlinx.serialization`의 `Json.parseToJsonElement`와 같은 것을 받아들이는 읽기 전용 JSON 파서 `xgs::json`을 새로 만들었다.
- **Kotlin과 일부러 다르게 한 것이 넷 있다**(아래 "Kotlin과 다르게 한 것"): 가사 매칭의 시그마(사용자 결정), JSON 배열 깊이 한계, 영상 ID 거절, 경로를 `Path` 대신 정리된 문자열로 받는 것. 둘째와 셋째는 실행 중에 controller가 정한 것이라 **사용자의 검토를 기다린다.**
- Kotlin 쪽에서 버그로 보이는 동작을 여럿 그대로 따랐다(아래 "고치지 않은 Kotlin 쪽 동작"). 바꿀지는 사용자가 정한다.
- 이 진술 밖에 있는 것: 프로세스 실행·도구 찾기·실제 yt-dlp·ffmpeg(Q2b), LRCLIB(Q2c), 작업·동시성·취소(Q2d), 구글 가사(Q3), 다른 Qt·JVM 버전, 아래 "확인하지 못한 것".

## `xgs::kt`에 더한 것

Task 1. 모두 `qt/core/text/kt_text.*`에 있고, 이식 코드는 Qt의 같은 일을 하는 함수 대신 이것을 쓴다.

- **`isLetterOrDigit(char32_t)`**(`Character.isLetterOrDigit(int)`): BMP는 Q1의 단위 판정, BMP 밖은 Qt의 범주(L*, Nd)에 JVM과 다른 코드 포인트를 표로 덮는다.
- **`nfkc`**(`java.text.Normalizer.normalize(s, NFKC)`): `QString::normalized(NormalizationForm_KC, QChar::Unicode_15_0)` 한 줄.
- **`toDoubleOrNull`**(Kotlin `String.toDoubleOrNull()`): `Double.valueOf(String)` 공개 문서의 문법을 직접 검사하고 값만 `std::from_chars`(로캘 무관)에 맡긴다.
- **`isAsciiSpace`**: Java 정규식 `\s`(플래그 없음)의 여섯 글자 `' '`, `\t`, `\n`, U+000B, `\f`, `\r`.

### Qt와 JVM이 달랐던 것과 예외 표의 크기

| 기능 | Qt 6.11.3 그대로 썼을 때 | 처리 | 예외 표 |
|---|---|---|---|
| BMP 밖 `isLetterOrDigit` | Qt는 유니코드 17.0, JVM 21은 15.0이라 Qt만 글자로 보는 코드 포인트가 있다(예: U+105C0~105F3, U+10940~10959, 가라이 문자, CJK 확장) | JVM의 답을 범위로 표에 둔다(`gen-tables.ps1`이 JVM의 공개 API에 물어 만든다) | **9,642개 코드 포인트, 42개 범위**(모두 JVM 답이 거짓) |

NFKC는 처음에 "JVM에는 없고 Qt에는 있는" 코드 포인트 10,615개를 장벽으로 두는 표를 만들었으나, 판 인자만 주어도 `Z`·`H`가 0이었고 장벽 코드 포인트마다 만든 탐침 63,689건도 장벽 유무와 상관없이 JVM과 같아서 표를 지웠다(Task 1의 실행). 문자열 수준에서만 드러나는 차이는 찾지 못했다. 짝 없는 서로게이트는 두 쪽 모두 그대로 둔다.

Task 1이 오라클로 관찰한 `toDoubleOrNull`의 답(모두 Javadoc의 문법과 맞았다): 앞뒤의 U+0020 이하 글자(NUL, U+001F 포함)는 무시하고 U+00A0·U+3000 같은 다른 공백이 있으면 `null`, `0x10`(지수 없음)은 `null`이고 `0x1p3`은 값, `1f`·`1d`는 값, `NaNd`·`Infinityf`는 `null`, `-NaN`은 부호 없는 NaN(`7ff8000000000000`), `1e400`은 무한, `2e-324`와 `0x1p-1075`는 0(짝수로 반올림), `4.9e-324`는 가장 작은 비정규 수, 다른 문자 체계의 숫자와 `1_000`, `1,5`는 `null`.

Task 1의 변이 확인(그 Task의 실행): BMP 밖 예외 표를 무시하면 `B` 9,642건, `nfkc`에서 판 인자를 빼면 `Z` 40건·`H` 1,396건, 실수 파싱의 앞 trim을 U+0020만으로 하면 `O` 1만 건 중 368건이 다르다. 모두 잡혔다.

## `xgs::json`

Task 3. `qt/core/json/json.*`. `parse`(실패면 없음), `find`(같은 키는 뒤 값), `dump`(대조용 정규형), `Primitive{isString, content}`, `Null`, `Object`(키 순서를 지키는 쌍의 목록), `Array`. 읽기, 복사, 소멸, 덤프 모두 재귀 없이 명시적 작업 목록으로 돈다. 그래서 객체 20만 단도 디버그 빌드에서 스택이 넘치지 않는다(`tst_json`의 깊이 시험이 파싱·복사·덤프·소멸을 모두 한다). 무엇을 받아들이는지는 **관찰한 Kotlin의 답으로만** 정했다. `kotlinx.serialization`의 소스는 보지 않았다.

### Kotlin이 표준 JSON 밖에서 받아들이는 것

`xgs::json`은 이것을 모두 똑같이 받아들인다.

1. 따옴표 없는 값(리터럴): `NaN`, `Infinity`, `-Infinity`, `01`, `+1`, `.5`, `1.`, `1e`, `0x10`, `1e999`, `TRUE`, `NULL`, `abc`, `'a'`, `1/*c*/`, `-`, `a-b_c$d`, U+00A0·U+FEFF·서로게이트가 든 것 등. 공백 넷, 제어 문자, `"` `,` `:` `[` `]` `{` `}` `\`가 아닌 단위의 연속은 모두 리터럴이다. 쓴 그대로가 `content`이고 `isString`은 거짓이다. 정확히 `null`만 null이다.
2. 최상위가 원시값(문자열, 리터럴)이어도 된다.
3. 문자열 안의 생 제어 문자(U+0000 포함), 줄바꿈, 탭, 짝 없는 서로게이트(생 것과 `\u` 이스케이프 둘 다).
4. 중복 키: 뒤의 값이 남고 자리는 처음 나온 자리다(`{"a":1,"b":2,"a":3}` → `a=3, b=2`). 키는 이스케이프를 푼 뒤 비교한다(`"\u0061"`과 `"a"`는 같은 키).
5. 배열에서 항목 뒤의 `]` 다음에 (공백을 지나) 값의 첫 글자가 오면 `]`가 쉼표처럼 동작한다: `[1]x]` → `[1, x]`, `[[a]]b]` → `[[a], b]`. 항목이 없는 배열(`[]b]`)이나 객체의 `}`(`{"a":1}"b":2}`)에는 없다.
6. 객체 사슬에는 깊이 한계가 없다(10^6단 성공).

받아들이지 않는 것: 따옴표 없는 키와 작은따옴표 키, 끝 쉼표, 겹친 쉼표, 주석(`//`, 값 앞의 `/*…*/`; 값 뒤의 `/*c*/`는 리터럴의 일부), 빈 입력, 공백뿐인 입력, 값 뒤의 쓰레기, U+0020·0009·000A·000D 밖의 공백(U+000B, 000C, 00A0, 2028, 3000, 0085, FEFF; 맨 앞 BOM 포함), `\x`·`\'`·`\U`·`\a`·짧은 `\u`, 닫히지 않은 문자열·객체·배열.

BOM으로 시작하는 파일은 Kotlin이 모두 없음으로 읽고 C++도 따른다(아래 "고치지 않은 Kotlin 쪽 동작" 1번). 이번 실행: `V`의 UTF-8 아닌 입력 11.9%, BOM으로 시작 3.2%, 불일치 0, Kotlin이 던진 사례 0. 10MB 시험은 이번 릴리스·디버그 테스트에서 통과했다 |
| 3. 자모가 풀린 한글, 전각 문자, 결합 문자의 정규화 | 표 `Z`(코드 포인트 전수 NFKC), 종류 `H`(무작위 문자열), 종류 `I`의 생성기(전각, 자모로 풀린 한글, 결합 문자, `H`의 재료) | Qt의 유니코드 판(17.0)을 그대로 쓰면 JVM(15.0)과 다르다. 판 인자로 맞췄다(위 "`xgs::kt`에 더한 것"). 이번 실행: `Z` 1,112,064개 불일치 0, `H`의 한글 자모가 든 입력 58.4%, 결합 문자 62.3%, 불일치 0 |
| 4. 숫자가 아닌 진행률 필드(`NA`, 빈 문자열, `1e3`, `0x10`, `Infinity`, 앞뒤 공백)와 0·음수 전체 크기 | 종류 `O`(`toDoubleOrNull`), 종류 `Q`(그 생성기의 값을 필드에 넣음) | Kotlin의 문법(16진은 `p` 지수가 있어야 함, 앞뒤 U+0020 이하만 무시 등)을 그대로 따랐다. 백분율이 NaN이 되는 경우 Kotlin의 `coerceIn`이 NaN을 남기는 것까지 같다(Task 4: 10만 건 중 94건이 NaN, 두 부호). 이번 실행: `O`의 NULL 39.3%, 무한·NaN 13.2%, `Q`의 `NULL` 27.9%, `P -` 23.1%, 값 49.0%, 불일치 0 |
| 5. 태그 값 속의 제어 문자·줄바꿈·끝의 역슬래시 | 종류 `A`(값의 60%에 `= ; # \`·LF·CR·탭·NUL·U+001B·U+007F를 1~3개, 25%는 끝에 `\` 1~3개) | 줄바꿈과 특수 글자는 역슬래시로 이스케이프되고, 탭·LF·CR이 아닌 U+0020 미만 제어 문자는 지워지며, 끝의 `\` 연속은 같은 수의 전각 역슬래시(U+FF3C)가 된다. 그래서 값이 다른 태그를 끼워 넣을 수 없다. 두 쪽이 같다. 이번 실행: 이스케이프된 글자가 든 답 99.0%, 전각 역슬래시 82.9%, 제어 문자가 지워진 사례 75.2%, 불일치 0 |

## Kotlin과 다르게 한 것

넷 모두 이 계획(넷째)이나 사용자(첫째)나 controller(둘째, 셋째)가 정한 것이다. **둘째와 셋째는 실행 중에 controller가 정했고 사용자가 아직 보지 않았다.** 바꾸려면 사용자가 정한다.

### 1. 가사 매칭의 시그마 (사용자 결정, 2026-11-15)

가사 매칭의 정규화(`words`)가 소문자로 바꾼 뒤 `ς`(U+03C2)를 `σ`(U+03C3)로 쓴다. 그래서 두 꼴이 같은 글자다. Kotlin은 다른 글자로 본다. Q1에서 `kt::lowercase`의 끝 시그마 선택이 JVM의 근사라서, 이렇게 하지 않으면 그리스어 제목의 매칭이 Kotlin과 어긋날 수 있었다.

| 입력 | Kotlin | C++ |
|---|---|---|
| `normalize("οδος")` | `οδος`(끝 `ς`) | `οδοσ` |
| `normalize("ΟΔΟΣ")` | (재지 않음) | `οδοσ` |
| `isMatch`: 질의 가수 `Band`, 제목 `ΟΔΟΣ-ΑΘΗΝΑΣ`; 후보 곡 `οδοσ-αθηνασ`, 가수 `Band`, 가사 3줄 | 거짓(`οδος…`와 `οδοσ…`가 다르다) | 참 |

(Kotlin과 C++의 답은 Task 7의 실행에서 잰 것이다.) C++ 전용 테스트 `sigmaFormsAreTheSameLetterInMatching`이 이 동작을 고정한다. 대조 종류 `I`는 모든 글에서 그 자체나 NFKC, 소문자, 그 결과의 NFKC가 `Σσς`를 낳는 코드 포인트(U+03F2, U+03F9, 수학 문자 시그마 등)를 빼고, 통계로 0건임을 확인한다(이번 관문 실행에서도 0건, 위 "대조").

### 2. JSON 배열 깊이 한계 (controller 결정, 실행 중; 사용자 검토 대기)

`xgs::json`은 배열이 동시에 1000개를 넘게 열리면 오류다. 객체는 세지 않는다. Kotlin에는 고정된 한계가 없다: 배열이 깊으면 kotlinx가 `StackOverflowError`를 던지는데, 그 깊이가 JVM 상태에 따라 실행마다 다르다(위 "깊이 관찰": 빈 배열 2216~11284단, 배열 사이 객체 1개면 1170~4783단). 그 `Error`는 `VideoInfoFile.read`의 `catch`(입출력 예외와 `IllegalArgumentException`만 잡는다)에 걸리지 않고 위로 올라간다. 따라 할 수 있는 고정된 Kotlin의 답이 없어서 controller가 이렇게 정했다.

| 입력 | Kotlin | C++ |
|---|---|---|
| `[`×1000 + `]`×1000 | 성공(관찰한 모든 실행) | 성공 |
| `[`×1001 + `]`×1001 | 이번 관찰에서는 성공(관찰 표 186행); 실행에 따라 다를 수 있다 | `ERR` |
| `[`×60000 + `]`×60000 | 늘 `StackOverflowError`(`ERR`) | `ERR` |
| 배열을 그렇게 깊이 겹친 `info.json` | `VideoInfoFile.read`가 `StackOverflowError`를 던진다(문서는 "던지지 않는다") | 앨범·설명·길이 모두 없음 |
| 객체 300000단 + 배열 + 객체 300000단 + `[1]` | 실패(설명하지 못함) | 성공 |

대조 생성기는 배열 1001~59999단을 만들지 않는다(그 구간의 Kotlin 답이 실행마다 달라서). 실제 yt-dlp `info.json`은 몇 단뿐이라 결과에 영향이 없다고 본다. 이 판단이 틀리면, 배열을 1001단 넘게 겹친 파일에서 Kotlin은 (그 실행에서 스택이 버티면) 앨범과 설명을 읽고 C++은 읽지 못한다.

### 3. 영상 ID 거절 (controller 결정, 실행 중; 사용자 검토 대기)

`downloadCommand`는 영상 ID가 비었거나 `\ / : * ? " < > |` 중 하나나 U+0000~001F 단위를 담으면 `std::invalid_argument`를 던진다. ID는 yt-dlp의 출력에서 오고 출력 경로(`<출력 폴더>\<ID>.%(ext)s`)에 그대로 이어지기 때문이다. Kotlin은 `outputDir.resolve("$videoId.%(ext)s")`로 잇는데, 그러면 `Path`의 해석이 ID에 적용되어 어떤 ID에서는 던지고 어떤 ID에서는 조용히 출력 폴더를 바꾼다. Task 6이 오라클로 본 Kotlin의 답(출력 폴더 `C:\out`):

| 영상 ID | Kotlin | C++ |
|---|---|---|
| (빈 문자열) | `C:\out\.%(ext)s` | 던짐 |
| `\` 또는 `/` | `C:\.%(ext)s`(폴더가 바뀜) | 던짐 |
| `a/b`, `a\b`, `a//b` | `C:\out\a\b.%(ext)s`(하위 폴더) | 던짐 |
| `:` 혼자 | 던짐 | 던짐 |
| `a:b` | `a:b.%(ext)s`(드라이브 상대 경로로 읽혀 출력 폴더가 사라짐) | 던짐 |
| `a*b`, `a?b`, `a"b`, `a<b`, `a>b`, `a|b`(혼자일 때도) | 던짐 | 던짐 |
| U+0001 혼자, U+0001 두 개 | 받음 | 던짐 |
| U+0009~000D 혼자 | 던짐 | 던짐 |
| `a`+U+0001, U+0001+`a` 등 다른 글자와 함께인 제어 문자 | 던짐 | 던짐 |
| `a `, `a.` | 받음(`C:\out\a .%(ext)s`, `C:\out\a..%(ext)s`) | 받음 |
| U+007F가 든 ID | 받음 | 받음 |
| `dQw4w9WgXcQ`, `a_b-c` | 받음 | 받음 |

C++이 더 엄격한 곳은 빈 ID, `\`, `/`, ID 안의 `:`, 그리고 Kotlin이 받는 제어 문자(혼자이거나 제어 문자로만 된 ID)다. 실제 영상 ID는 `[A-Za-z0-9_-]` 11자라서 정상 사용에서는 차이가 없다. 이 판단이 틀리면, 그런 글자가 든 정상 ID가 내려받기 전에 크게 실패한다. C++ 전용 테스트 `downloadRejectsAVideoIdThatIsNotAPlainFileNamePart`가 이 규칙을 고정한다. 대조 생성기는 Kotlin도 던지는 글자는 그대로 넣어 두 쪽의 `ERR`을 비교하고, C++만 던지는 입력만 바꾼다(빈 ID는 `id`로, `\ / :`는 지우고, 영문자·숫자가 없는 ID의 제어 문자는 지운다).

### 4. 경로는 이미 정리된 문자열로 받는다 (계획 결정)

Kotlin은 `java.nio.file.Path`를 쓰고, 그 해석과 정리(`/`를 `\`로, 겹친 구분자 합치기, `resolve`의 드라이브 처리 등)가 명령 인자에 그대로 반영된다. C++은 `QString`을 받아 **그대로** 쓰고 그 정리를 옮기지 않았다(Qt의 경로 정리 함수도 금지 목록에 있다). 예: Kotlin 테스트의 `Path.of("C:/music/a.m4a")`는 `C:\music\a.m4a`로 인자에 들어가지만, C++에 `C:/music/a.m4a`를 주면 인자에 `C:/music/a.m4a`가 들어간다. 대조 종류 `K`는 정리된 Windows 절대 경로만 넣고, 오라클은 `Path.of(text).toString()`이 글자와 다르면 `BADPATH`라고 답해 생성기 문제를 드러낸다(이번 실행에서 그런 답이 있으면 불일치로 나타났을 것이고, 불일치는 0이다).

**호출하는 쪽(Q2b)이 보장해야 하는 것**: `ytdlp_commands.h`, `ffmpeg_commands.h`, `video_info_file.h`에 받는 경로는 드라이브 글자 + `\`로 나뉜 부분, 끝 구분자 없음, 빈 부분·`.`·`..` 부분 없음, 끝 공백·끝 점 없는 Windows 절대 경로여야 한다. 사용자가 고른 폴더, 설정에서 읽은 경로, 도구 경로를 이 모양으로 만들어 넘기는 것은 Q2b의 일이다. 이 모양 밖의 경로에서 C++과 Kotlin이 같은 인자를 만든다는 보장은 없다.

## 고치지 않은 Kotlin 쪽 동작

모두 **Qt 판이 그대로 따른다**(대조에서 같은 답). 바꿀지는 사용자가 정한다. 바꾸려면 Kotlin 쪽을 먼저 바꾸고 대조를 다시 돌린다. 입력과 답은 각 Task의 실행에서 잰 것이다.

1. **BOM으로 시작하는 `info.json`은 모든 값이 없음이 된다**(Task 5). `Files.readString`이 BOM을 떼지 않아 U+FEFF가 JSON 앞에 남고, kotlinx는 그것을 공백으로 보지 않아 거절한다. 입력 `EF BB BF` + `{"album":"A"}` → 앨범·설명·길이 모두 없음. yt-dlp는 BOM을 쓰지 않으므로 실제 영향은 없을 것이다.
2. **`ERROR:` 뒤에 아무것도 없으면 메시지가 빈 문자열이다**(Task 4). `summarize`가 `ERROR:` 줄을 찾으면 그 나머지를 쓰고, 비어 있어도 "마지막 비지 않은 줄"로 돌아가지 않는다. 입력 stderr 한 줄 `ERROR:` → 종류 `OTHER`, 메시지 `""`.
3. **`take(300)`이 서로게이트 쌍을 자를 수 있다**(Task 4). 메시지를 UTF-16 단위 300개로 자르므로 300번째 단위가 이모지의 앞 반쪽이면 메시지가 짝 없는 높은 서로게이트로 끝난다. 대조 `E`의 생성기가 300 단위 자름 자리에 이모지를 넣고, 두 쪽이 같은 짝 없는 서로게이트를 낸다.
4. **배열에서 `]`가 쉼표처럼 동작한다**(Task 3, kotlinx의 동작). `[1]x]` → `[1, x]`, `{"a":[1]x]}` → `{"a":[1, x]}`. 위 "Kotlin이 표준 JSON 밖에서 받아들이는 것" 5번.
5. **깊은 배열의 `StackOverflowError`가 `VideoInfoFile.read` 밖으로 나간다**(Task 3·5). 위 "Kotlin과 다르게 한 것" 2번. 이것만은 C++이 따르지 않는다(C++은 없음을 준다).
6. **후보의 길이가 NaN이면 길이 검사를 통과한다**(Task 7). `NaN > 8.0`이 거짓이라서다. 질의 258초, 후보 `duration = NaN`(제목·가수·가사는 맞음) → `isMatch` 참. +무한은 거절된다. `pick`에서는 NaN이 가장 큰 값으로 정렬된다(`Double.compare` 순서): `pick [NaN, 없음]` → 인덱스 1(없음의 차는 `Double.MAX_VALUE`).
7. **`Lived`는 버전 표지가 아니다**(Task 7). 버전 낱말 정규식에 맞지 않는 낱말(`Lived`, `Liveds`)은 표지가 아니어서, 질의 `Hello`가 후보 `Hello (Lived)`와 맞는다(참). 의도된 동작일 수도 있다.
8. **결과에 영향이 없는 Kotlin 코드**(Task 7): `LIVE_LIKE_WORD`의 `d` 갈래와 `hasVersionMarker` 안의 소문자 변환. 위 "변이 시험"의 동치 변이 (2), (3). 옮기기는 했다.
9. **`Path.resolve`가 영상 ID를 해석한다**(Task 6). 위 "Kotlin과 다르게 한 것" 3번. 이것은 C++이 따르지 않는다.
10. **비문자와 가운데 BOM은 값에 남는다**(Task 5, 관찰). U+FFFE, U+FFFF, U+FDD0, U+10FFFF, 문자열 가운데의 U+FEFF는 UTF-8로 올바르므로 앨범·설명에 그대로 남는다(`trim`은 U+FEFF를 공백으로 보지 않는다). 버그라기보다 관찰이다.
11. **속도 제한과 목록으로 정한 TRANSIENT 실패는 `summarize` 결과를 메시지로 쓴다**(Task 4). 그래서 메시지가 길거나(300 단위까지) 비어 있을 수 있다.
12. **크레딧·공백 정규식의 경계**(Task 7, 관찰): Java 정규식 `\s`는 U+001C, U+0085, U+00A0과 맞지 않고 U+000B, U+000C와는 맞는다. 그래서 `Title`+U+001C+`feat. X`에서는 크레딧이 떨어지지 않고 제목 변형은 입력 그대로 하나다(U+0085, U+00A0도 같다). `[0-9]`는 ASCII 숫자만이라 `Remix٣`(아랍-인도 숫자)는 표지가 아니다. 버그라기보다 정규식을 그대로 옮긴 결과다.

Q1 보고서의 "고치지 않은 Kotlin 쪽 동작" 일곱 가지와 최종 리뷰가 본 넷은 그대로 남아 있다(이번 단계에서 다루지 않았다).

## 옮기지 않은 것

- **`engine`의 나머지**: 프로세스 실행(`ProcessRunner`), 도구 찾기·설치(`ToolLocator`, `DefaultToolManager`), yt-dlp 조회(`YtDlpResolver`), m4a 태그 쓰기(`M4aTagger`), 출력 폴더(`LocalFolderSink`, `OutputSink`) → Q2b. LRCLIB(`LrclibLyricsProvider`, `FallbackLyricsProvider`, `LyricsProvider`) → Q2c. 작업·동시성·취소(`DefaultDownloadService`, `ItemDownloader`, `Services`) → Q2d. 구글 가사(`engine/lyrics/google`) → Q3. 그 테스트들과 테스트 도우미(`FfmetadataReader`와 그 테스트, `Fakes`, 통합 테스트)도 해당 단계에서 옮긴다.
- **`ApiModels`의 전송용 형**: `ResolveRequest`, `JobRequest`, `JobCreated`, `ActionResult`, `ErrorResponse`, `ApiJson`, `ApiHeaders`, `sseName`, `BrowserCommand`, `BrowserAnswer`. Qt 판에는 HTTP도 JSON 전송 형식도 없다. 도메인 형(`ResolvedItem`, `ResolveResult`(Kotlin `ResolveResponse`), `JobOptions`, `Stage`, `JobStatus`, `JobSummary`, `LyricsOutcome`, 작업 이벤트, `ToolInfo`, `ToolsStatus`, `ToolPaths`, `LyricsQuery`)은 `qt/core/model/models.h`에 JSON 없이 만들었다.
- **`Path`의 정리 동작**: 위 "Kotlin과 다르게 한 것" 4번.
- **JSON 쓰기와 형 지정 역직렬화**: `xgs::json`은 읽기만 한다(덤프는 대조용 정규형이다).

## 확인하지 못한 것

- **배열 1001~59999단 JSON.** Kotlin의 답이 실행마다 달라 대조하지 않았다. 객체가 여럿 낀 깊은 배열과, 설명하지 못한 객체 30만 단 사례도 대조 밖이다.
- **`Path` 정리가 필요한 경로.** 대조는 정리된 Windows 절대 경로만 넣었다. UNC 경로(`\\server\share`), `\\?\` 접두어, 상대 경로, `/` 구분자, 260자를 넘는 경로는 시험하지 않았다.
- **명령이 실제 프로세스로 넘어가는 모양.** 대조는 인자 목록을 목록으로 비교했다. 그 목록이 Windows 명령줄로 바뀔 때의 인용(Kotlin `ProcessBuilder`와 Qt `QProcess`)은 비교하지 않았다(아래 "Q2b에 넘길 것").
- **태그 파일을 디스크에 쓰는 것.** `renderFfmetadata`의 문자열만 비교했다. Kotlin은 그것을 UTF-8로 쓴다(`Files.writeString(…, UTF_8)`). 값에 짝 없는 서로게이트가 있을 때 Kotlin의 쓰기가 무엇을 하는지는 관찰하지 않았다.
- **`automaticConcurrency`**: 대조하지 않았다(위).
- **다른 Qt·JVM 버전.** Qt 6.11.3과 JVM 21.0.9에서만 돌렸다. 둘 중 하나가 바뀌면 `gen-tables.ps1`을 다시 돌리고 `U`·`X`·`S`·`B`·`Z`·`H`를 다시 돌려야 한다. NFKC 예외가 0인 것은 Qt가 판 인자를 문서대로 지키는 데 기댄다.
- **실수 파싱의 넘침 판정**은 MSVC `from_chars`의 관찰된 동작(비정규 값은 그대로, 0이나 무한일 때만 범위 오류)에 기댄다. 다른 컴파일러는 시험하지 않았다.
- **단언의 같음.** `test-names.ps1`은 이름만 본다. 157개 테스트의 단언이 Kotlin과 같은지는 각 Task의 구현자와 리뷰어가 보았고 Task 8은 다시 보지 않았다.
- **seed가 적다.** 이번 관문 실행은 1만 건 seed 셋과 10만 건 seed 하나(424242)다. 각 Task는 자기 종류를 다른 seed(42, 777, 4242, 20261116)로도 돌렸다고 적었으나 그것은 그 Task의 실행이다.
- **통계는 근사다.** 여러 통계는 `run.ps1`이 규칙을 다시 쓴 근사로 센다(예: `V`의 "UTF-8이 아닌 입력", `I`의 "부분 문자열 가수 짝"). 답의 비교는 정확하다.
- **시간 한도.** 10MB `info.json`의 3초, 10MB JSON 문서의 3초는 릴리스에서만 확인한다. 이번 실행에서 시험 하나하나의 시간은 따로 찍지 않았다(위 "테스트").
- **사용자 결정을 기다리는 것.** 배열 깊이 한계와 영상 ID 거절(위 2, 3번)은 사용자가 아직 보지 않았다.
- **Q1·Q0에서 열려 있는 것**은 그대로다(Q1 보고서의 "확인하지 못한 것").

## Q2b에 넘길 것

- **경로를 정리해 넘길 책임.** 명령 조립과 정보 파일 읽기는 받은 경로 문자열을 그대로 쓴다. Q2b는 사용자가 고른 폴더, 설정, 도구 경로를 드라이브 글자 + `\`로 나뉜 부분, 끝 구분자 없음, 빈·`.`·`..` 부분 없음의 Windows 절대 경로로 만들어 넘긴다(위 "Kotlin과 다르게 한 것" 4번). 이 정리를 Qt의 경로 함수로 할지는 Q2b가 정한다. 이식 코드(`qt/core`)에서는 금지 목록 때문에 쓸 수 없으므로 정리는 호출하는 층에 두거나 금지 목록의 예외를 정해야 한다. UNC·긴 경로를 어떻게 다룰지도 정해야 한다.
- **`parseVideoInfo`가 받는 바이트.** `parseVideoInfo(const QByteArray&)`는 파일의 바이트를 **그대로** 받는다: UTF-8로 엄격히 디코드하고(잘못된 열이면 모두 없음), 맨 앞 BOM을 떼지 않는다(그러면 모두 없음, Kotlin과 같음). `readVideoInfo(path)`가 `QFile`로 읽어 이것을 부른다. Q2b는 바이트를 미리 디코드하거나 BOM을 떼거나 줄바꿈을 바꾸지 말아야 한다. 파일을 읽는 동안 yt-dlp가 아직 쓰고 있을 수 있는지(잘린 파일은 대개 "모두 없음")는 Q2b가 순서로 막는다.
- **명령 인자를 `QProcess`에 넘길 때의 인용.** `ytdlp_commands`와 `ffmpeg_commands`는 인자 목록(`QStringList`)을 낸다. 대조는 이 목록이 Kotlin의 목록과 같음만 보였다. Windows에서는 목록이 명령줄 하나로 합쳐지고 받는 프로그램이 다시 나눈다. Kotlin의 `ProcessBuilder`와 Qt의 `QProcess`가 공백, `"`, 끝의 `\`, 빈 인자, `%`·`&`가 든 인자를 같은 명령줄로 만든다는 보장은 확인하지 않았다. 출력 경로 틀 `%(ext)s`, `--print` 틀, 공백·`&`·`%`가 든 폴더, 끝이 `\`인 값이 실제 yt-dlp·ffmpeg에 글자 그대로 닿는지 Q2b의 통합 테스트(예: 받은 인자를 그대로 적는 작은 프로그램)로 확인해야 한다. 도구 경로가 `.cmd`·`.bat`이면 Windows가 `cmd.exe`를 거치므로 `%`·`&`·`^`가 해석될 수 있다(js 런타임 경로는 yt-dlp에 인자로만 넘기므로 우리가 실행하지 않는다).
- **영상 ID 규칙.** `downloadCommand`는 빈 ID와 `\ / : * ? " < > |`·U+0000~001F가 든 ID에 `std::invalid_argument`를 던진다(Kotlin은 일부만 던진다). Q2b·Q2d는 이 예외를 잡아 그 곡만 실패로 처리해야 한다(Kotlin은 일부 ID에서 `InvalidPathException`이 났을 자리다). 다른 함수들도 `ytDlp` 경로가 없으면 `std::invalid_argument`를 던진다. `tagCommand`는 출력 파일이 `.m4a`로 끝나지 않으면 던진다.
- **태그 파일 쓰기.** `renderFfmetadata`는 `QString`을 낸다. Kotlin은 그것을 BOM 없는 UTF-8로 쓴다(`M4aTagger`). Q2b가 같은 인코딩으로 써야 하고, 값의 짝 없는 서로게이트를 쓸 때 Kotlin이 무엇을 하는지는 관찰해서 맞춰야 한다(위 "확인하지 못한 것").
- **동시 다운로드 수.** `automaticConcurrency`는 `QThread::idealThreadCount()`(논리 프로세서 수)를 쓴다. Kotlin의 값과 같은지는 Q2d에서 실제 PC로 확인한다.
- **오류 분류에 넘길 stderr 줄.** `classifyError`는 줄 목록을 받는다. 빈 줄을 대조가 실제로 보내지 않았다(위 "남은 사소한 것"). Q2b가 stderr를 줄로 나눌 때 `\r\n`·`\r`과 빈 줄을 Kotlin의 `ProcessRunner`와 같게 다루는지 확인해야 한다.
- **시그마 결정의 범위.** 사용자 결정은 가사 매칭에만 적용됐다. Q1 보고서가 함께 짚은 `engine/lyrics/google/GoogleSearchQuery.kt`의 캐시 키(사용자 글을 소문자로 바꿔 쓴다)는 Q3에서 같은 문제를 만난다. 그때 다시 정해야 한다.
- **대조 종류를 더하는 법과 관문**은 `qt/README.md`에 있다(이번 단계에서 종류 `B Z H O J E Q V K A I`를 더했다). 새 종류도 1만 건 seed 셋과 10만 건으로 돌리고, 변이로 생성기를 시험한다.
- **JDK·kotlinx 소스를 보지 않는다.** 차이는 오라클로만 정한다. `server/build/sidecar-image`가 오래되면 `run.ps1`이 실패한다(Gradle은 사용자가 정할 때 돌린다).

## 판정

**Q2a 관문(설계 §4의 Q2 행 중 이 계획의 몫)은 충족됐다.** 이식 대상 `engine` 테스트 157개는 같은 이름으로 모두 통과하고(이름 대조에서 빠진 것 0, Q1의 193개 포함 13개 클래스), 릴리스와 디버그의 깨끗한 빌드에서 테스트 17개 실행 파일이 모두 통과했으며, 금지 호출은 0건이고, 대조는 네 번의 실행(1만 건 seed 셋, 10만 건 seed 하나, 모두 한 번의 호출로 24개 종류 전부)에서 모든 종류가 불일치 0이고 통계 문턱도 넘었다. 이 실행은 Task 8에서 처음부터 한 번 돌린 것이고, 그 사이 C++을 고치지 않았다.

이 진술이 다루지 않는 것: 실제 프로세스·파일 시스템·네트워크(Q2b~Q2d), 정리되지 않은 경로, 배열 1001~59999단 JSON, 명령줄 인용, 다른 Qt·JVM 버전, 단언의 같음을 다시 본 것. 사용자가 정할 것: 배열 깊이 한계(1000)와 영상 ID 거절을 받아들일지, 위 Kotlin 쪽 동작들을 바꿀지. Q1에서 남은 결정(예전 로컬 커밋 정리, Q1의 Kotlin 동작들)도 그대로다.
