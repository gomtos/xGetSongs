## 막힌 점과 고친 것

- 계획대로 진행했고 계획에서 벗어난 것은 없다. 코드와 테스트는 계획서를 쓰며 스크래치에서 이미 돌려 본 파일을 그대로 저장소에 옮겼고, 옮길 때마다 계획서 본문과 글자가 같은지 대조했다.
- 계획서의 Task 9 Step 1이 `sidecar-host`의 통합 시험을 "1 ignored"로 적었으나 실제로는 `real_download`와 `real_sidecar`가 각각 1개씩 `#[ignore]`라 2개다(2단계 이후 `real_download`가 더해졌다). 동작에는 영향이 없다.
- 이번 점검의 영상 다운로드는 10초였다(계획을 쓰며 본 값은 24초). 같은 코드이고 네트워크 상태 차이로 본다.
- 시작 직후 닫기는 2단계(2.7~3.0초)보다 조금 느린 3.3~3.4초였다. 한도(15초)에 한참 못 미치고 점검 페이지가 이번엔 같은 창에서 화면까지 불러오는 빌드라서 생기는 차이로 본다. 원인을 따로 가리지는 않았다.

## 최종 리뷰 뒤 고친 것

전체 브랜치를 새 맥락의 리뷰어(opus)가 한 번 읽었다. Critical은 없었고 Important 하나와 Minor 열둘이었다. 지적을 코드에서 일일이 확인한 뒤, 사실인 것은 먼저 실패하는 테스트나 시나리오로 재현하고 고쳤다.

- **Important: 이 보고서의 프레임 간격이 화면의 값이 아니었다.** 첫 판은 `worstFrameGapMs` 161ms를 "같은 창에서 101행 목록과 진행 갱신까지 한 뒤의 값"이라고 썼지만, 그 값은 점검 페이지가 사이드카를 기다리는 동안 잰 것이었다. 진행 갱신이 화면을 끊지 않는다는 근거(Review Focus 3)가 실제 셸에서는 없었던 셈이다. `check-screen.ts`가 영상 한 곡과 재생목록(8곡 동시)을 받는 동안 프레임 간격을 직접 재도록 하고 다시 쟀다: 둘 다 17ms. 표의 해당 줄을 바로잡았다.
- **`holder`의 경쟁 둘과 시계(테스트 3개, 먼저 실패를 확인):** 새 작업의 id가 오기 전에 누른 `취소`가 이미 끝난 이전 작업을 취소하던 것(`cancelBeforeTheNewJobHasAnIdDoesNotCancelThePreviousJob`), 옛 작업의 이벤트 스트림이 뒤늦게 끝나면 새 작업을 `서버와의 연결이 끊어졌습니다.`로 끝내던 것(`theEndOfAnOldWatchDoesNotMarkTheNewJobAsLost`), 소요 시간이 벽시계를 따르던 것(`theElapsedTimeDoesNotFollowTheWallClock`, 기본 시계를 `performance.now()`로). 앞의 둘은 Kotlin 원본에도 있는 경쟁이다.
- **화면(시나리오 E로 먼저 실패를 확인):** 순위 칸을 IME가 조합하는 도중에 덮어쓰던 것(조합이 끝날 때 걸러서 반영), 순위 칸을 비운 뒤 다른 칸을 바꾸면 이전 숫자로 다시 채워지던 것(Compose처럼 순위가 바뀌었을 때만 맞춘다), 바뀌지 않은 오류 문구·제목·저장 위치를 진행 이벤트마다 다시 쓰던 것(`role="alert"` 배너를 스크린 리더가 다시 읽을 수 있다), 작업이 실패 없이 끝나면 키보드 포커스가 페이지로 떨어지던 것, 앨범명 칸의 맞춤법 밑줄.
- **확인 도구와 점검 테스트:** 대조 도구가 `classify`의 `trim`을 JS의 것으로 바꿔도 못 잡던 것(입력 둘레 글자를 넓히고 `theWhiteSpaceAroundAnAddressIsKotlinsNotJavaScripts`를 더했다. 일부러 바꾸면 이제 단위 테스트와 도구가 모두 잡는다), 잘못된 인자로 0건을 돌려도 통과하던 것과 오라클의 답 수가 맞지 않아도 통과하던 것, `shared`의 Kotlin 테스트 파일이 옮겨지거나 이름이 바뀌어도 점검 테스트가 조용히 건너뛰던 것(이제 `app/`의 스위트만 건너뛴다).
- **그 밖:** `vite.config.ts`의 옛 주석, `lib.rs`의 빈 줄.
- **Kotlin 원본과 다른 점(의도한 것과 알게 된 것):** 순위 칸은 ASCII 숫자만 받는다(의도). Enter로 조회가 된다(브라우저 폼의 동작이고 Compose에는 없었다). 리뷰 전에 있던 다른 두 차이(순위 칸을 다시 채우는 규칙, 벽시계)는 위에서 원본에 맞췄다.
- **미룬 것(리뷰의 Minor):** 도구 카드가 다시 그려질 때 그 안의 단추가 가졌던 키보드 포커스를 잃는다(비활성이 되는 단추라 포커스를 되돌릴 설계가 필요하다), 데모 서버가 실제 서버의 계약과 다른 곳들(출력 폴더 검증, `item-skipped`, 같은 작업을 두 번 보기, 끝난 작업의 취소, 영상 순위 범위: 개발용이다), 데모가 제품 번들에 정적으로 들어간다. 새 작업이 시작되는 수십 ms 안에 누른 `취소`는 무시된다(미뤄서 보내지 않는다. 첫 작업에서는 Kotlin 원본도 같다).

## 사용자가 직접 확인할 것

이 단계의 화면은 폴더 선택 창과 탐색기 열기가 없고(출력 폴더는 직접 입력) 옵션이 다음 실행에 저장되지 않는다(4단계). 그 밖의 것은 실제로 써 볼 수 있다:

- 일반 빌드(`npm run tauri build -- --no-bundle`)를 만들어 `shell\src-tauri\target\release\shell.exe`를 실행한다.
- 한글 입력: 주소, 출력 폴더, 앨범명 칸에 한글을 입력·조합하고(조합 밑줄, 커서), 붙여넣기·선택·우클릭 메뉴를 써 본다. 다운로드 중에 한글을 입력해도 글자가 깨지지 않는다.
- 키보드만으로 조회부터 다운로드 시작까지, Enter로 조회, Tab 순서, 다크·라이트 설정.
- 실제 재생목록 조회와 다운로드, 도중 취소, 실패 항목 재시도.

## 이 단계가 확인하지 않은 것

- 실제 한글 IME 조합 중의 입력(자동으로 시험할 수 없다. 코드는 조합 중인 입력란에 값을 쓰지 않고, 순위 번호 칸까지 포함해 시나리오 E가 합성한 조합 이벤트로 확인했을 뿐이다). 직접 확인할 때는 **순위 번호 칸**(영상 한 곡을 조회하면 나온다)에도 한글 모드로 입력해 본다.
- 999곡 목록의 성능(확인은 100곡·101곡이다).
- 우클릭 메뉴의 새로고침(F5·Ctrl+R은 막았다). 새로 읽으면 화면은 처음 상태로 돌아가지만 작업은 서버에서 계속 받는다. 그 작업의 이벤트는 다시 받을 수 없어서(서버가 한 번만 받게 한다) UI에서 취소할 수 없고 앱을 닫아야 끝나며, 같은 폴더로 겹치는 작업을 새로 시작할 수도 있다. 해결은 서버 쪽 재접속이 필요하다.
- `install_yt_dlp`와 `update_yt_dlp`의 실제 호출(내려받는 호출이라 데모에서만 확인했다).
- 점검 실행은 한 번이다. 시간 값은 반복 측정이 아니다.
- 2단계에서 넘어온 항목: 사이드카가 실행 중에 죽는 경우, Job Object 생성 결과의 기록, 셸에 로거를 붙일 때의 `ureq` 로그의 토큰.
