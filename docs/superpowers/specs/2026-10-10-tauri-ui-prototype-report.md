# Tauri UI 프로토타입 보고서

작성일: 2026-10-10
설계: [2026-10-10-tauri-kotlin-sidecar-design.md](2026-10-10-tauri-kotlin-sidecar-design.md) §5.2
계획: [2026-10-10-tauri-ui-prototype.md](../plans/2026-10-10-tauri-ui-prototype.md)

환경: Windows 11 Home 10.0.26200, 시스템 다크 모드(`AppsUseLightTheme=0`), 화면 배율 레지스트리 `AppliedDPI=96`·`LogPixels=120`(배율은 확정하지 못함), WebView2 154.0.4258.62, Tauri 2 / Rust 1.99.0 / Vite 8.3.4 / TypeScript 6.0.3. 비교한 앱은 이 저장소의 Compose 앱(`run.bat`)과 `shell/`의 프로토타입(`npm run tauri dev`)이다.

## 이 보고서가 확인한 것과 확인하지 못한 것

사용자가 항목별로 확인하지 않고 두 화면을 직접 써 본 뒤 U1의 판단과 가장 큰 이점 한 가지를 알려 주었다. 그래서 아래 표는 **사용자가 확인한 것**, **제가 측정한 것**, **확인하지 못한 것(미확인)**을 구분해서 적는다. 미확인은 통과가 아니다.

## UI 관문

| 번호 | 조건 | 결과 | 근거 |
|---|---|---|---|
| U1 | 사용자가 보고 "Compose보다 낫다" | **통과** | 사용자: "프로토타입이 Compose보다 나아, 특히 파일 목록에서 파일명 복사가 가능하네". 상태별(빈 화면, 미리보기, 다운로드 중, 오류) 판단은 따로 받지 않았다 |
| U2 | 한글 입력 | 일부 확인, 나머지 미확인 | 아래 표 |
| U3 | 글꼴 | 미확인 | 아래 |
| U4 | 네이티브 느낌 | 일부 확인, 나머지 미확인 | 아래 표 |

### U2 한글 입력

| 항목 | Compose | 프로토타입 |
|---|---|---|
| 목록의 글자 선택·복사 | 불가(코드상 `PreviewList.kt`의 `Text`가 `SelectionContainer` 밖에 있다) | **가능** (사용자 확인, 이점으로 꼽음) |
| 조합 중인 글자 | 미확인 | 미확인 |
| 한/영 전환 | 미확인 | 미확인 |
| 붙여넣기 | 미확인 | 미확인 |
| 선택(드래그, 더블클릭, `Ctrl+A`) | 미확인 | 미확인 |
| 복사·잘라내기 | 미확인 | 미확인 |
| 우클릭 메뉴 | 미확인 | 미확인 |
| 갱신 중 입력 | (해당 없음) | 미확인 (코드는 입력란을 다시 그리지 않고 행만 고치게 짰다) |

### U3 글꼴

미확인. 프로토타입은 `"Segoe UI Variable Text", "Segoe UI", "Malgun Gothic", system-ui` 순서로 시스템 글꼴을 요청한다(`prototype.css`). 실제로 어떤 글꼴로 그려졌는지, Compose와 선명도가 어떻게 다른지는 확인하지 못했다.

### U4 네이티브 느낌

| 항목 | Compose | 프로토타입 |
|---|---|---|
| 시스템 테마 | 미확인(코드상 `MaterialTheme` 기본 색이라 라이트 고정일 것으로 예상) | **다크를 따름** (제가 Tauri 창을 캡처해서 확인. 시스템이 다크일 때만 봤고 라이트 전환은 미확인) |
| 강조색 | 미확인 | 파란 기본 버튼이 보였다. 시스템 강조색을 바꿔서 따라가는지는 미확인 |
| `Enter`로 조회 | 미확인 | Chromium 브라우저에서 키 입력으로 확인. WebView2 창에서는 미확인 |
| `Tab` 순서, 키보드만으로 조작 | 미확인 | 미확인 |
| 낭독기(Narrator) | 미확인 | 미확인 |
| 창 조작 | 미확인 | 제목 표시줄은 시스템 다크 설정을 따랐다. 최대화·스냅은 미확인 |

## 악화 한도

| 항목 | 결과 |
|---|---|
| 100행 목록을 초당 10회 갱신(8행)하면서 스크롤해도 끊기지 않음 | **끊김 없음(메인 스레드 기준)**. Chromium에서 6초 동안 8행 갱신 + 스크롤, DOM 변경 1,818회(초당 약 300회): 이벤트 루프 지연 중앙값 0.7ms, 99번째 백분위 2.4ms, 최대 2.7ms, 긴 작업(50ms 이상) 0건. 화면이 숨겨진 상태라 프레임 간격은 재지 못했고 WebView2 창에서는 재지 않았다. 사용자는 끊김을 언급하지 않았다 |

## 관찰

- 기본 창 크기(1000×760)에서는 도구 패널과 옵션이 높이를 많이 차지해서 곡 목록이 1~2줄만 보인다. Compose 화면도 같은 구성이라 비슷할 것으로 보이며(미확인), 3단계(프런트엔드 이식)에서 옵션을 접는 등 구성을 다시 볼 만하다.
- 사용자가 꼽은 이점인 목록 문구 복사는 Compose에서도 `SelectionContainer`로 감싸면 가능한 것으로 알려져 있다(이 저장소에서 시도하지는 않았다). 따라서 U1의 나머지 이유(한글 입력, 글꼴, 네이티브 느낌)가 마이그레이션의 근거가 되는지는 위의 미확인 항목이 채워져야 분명해진다.

## 막힌 점과 고친 것

- 스캐폴드의 TypeScript가 6.0이라 CSS import(`import "./prototype.css"`)에 타입 선언이 필요했다(TS2882). `src/vite-env.d.ts`(`/// <reference types="vite/client" />`)를 추가했다.
- 사용자 요청으로 `조회`와 `폴더 선택` 버튼을 옆 텍스트박스와 수직으로 맞췄다. 원인은 라벨이 위에 붙은 입력란과 버튼을 가운데 정렬한 것이었고, 두 행을 아래 기준으로 맞추고 버튼 높이를 입력란과 같게(34.3px) 했다. 위·아래 좌표 차이가 0.00이다.
- 그 밖의 계획과 다른 점은 없다. Rust 설치(`rustup` 1.29.1, `rustc` 1.99.0)와 첫 Tauri 컴파일(3분 50초)은 계획대로였다.

## 판정

**통과.** 설계 §5.2는 U1이 사용자의 판단이고 "U1이 낫다가 아니면 중단"이라고 정했으며, 사용자가 "낫다"고 판단했다. U2~U4는 항목별로 확인하지 않았지만 실패로 보고된 항목이 없다. 다만 위의 미확인 항목이 많아서, 다음 단계로 갈 때 두 가지를 정해야 한다.

1. 0b 스파이크(사이드카 진입점, Rust 크레이트, 프로세스 정리)로 진행할지. 이 보고서가 UI 관문을 통과시켰으므로 설계상 다음은 0b다.
2. 미확인 항목(특히 한글 조합 입력, 글꼴 선명도, 라이트 모드, 키보드 조작)을 지금 확인할지, 3단계(프런트엔드 이식)에서 실제 화면으로 확인할지. 프로토타입은 이 확인에 그대로 쓸 수 있고 `Win+Ctrl+Enter`(Narrator), 화면 배율 변경 등 사용자의 시스템 설정이 필요하다.
