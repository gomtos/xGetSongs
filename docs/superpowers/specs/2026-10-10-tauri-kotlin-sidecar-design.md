# Tauri(UI) + Kotlin(로직) 사이드카 마이그레이션 설계

작성일: 2026-10-10

## 1. 목표와 동기

- **목표:** 화면을 Compose Desktop에서 Tauri(웹뷰)로 옮기고, 로직(`shared`, `engine`, `server`)은 지금의 Kotlin 코드를 그대로 쓴다. 마지막에 `app`(Compose UI)을 지운다.
- **동기: UI 품질** (2026-10-10 확정). 이 마이그레이션이 주는 이득은 화면이 Compose Desktop보다 나아지는 것 하나다. 크기와 시작 속도는 개선 목표가 아니다. 나빠지지 않는 한도(§5.1 악화 한도)만 지킨다.
- 그래서 관문이 둘이다. 기술 관문(사이드카가 안전하게 뜨고 꺼지는가)과 **UI 관문**(화면이 정말 나아지는가, §5.2). 사이드카와 포장에는 비용이 많이 들고 그 비용은 모두 UI 품질을 위한 것이므로, UI 관문을 먼저 확인한다.
- 웹 이전과의 관계: 설계 문서 §10.3은 Compose for Web이 Beta라서 최악의 경우 웹 UI만 HTML로 대체한다고 적었다. 이 마이그레이션의 프런트엔드가 그대로 그 웹 UI가 된다.

## 2. 확정된 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 연동 패턴 | **사이드카 독립 프로세스.** Kotlin 서버를 별도 JVM 프로세스로 띄우고 Tauri(Rust)가 제어한다 | 아래 2.1 |
| 사이드카와의 통신 | 지금의 Ktor HTTP + SSE + 토큰을 그대로 쓴다 | 계약(`ApiModels`)과 테스트(`RoutesTest`, `LocalServerTest`, `HttpXgsApiTest`)가 이미 있다. 서버 쪽 변경이 가장 작다 |
| 프런트엔드가 서버를 부르는 길 | **Rust 브리지.** 프런트엔드는 `invoke`/이벤트만 쓰고, HTTP·SSE는 Rust가 한다 | 2.2 |
| 시작 신호 | 사이드카가 서버가 열리면 stdout에 한 줄을 쓴다: `XGS-READY <port> <token>` | 포트는 임의(0)이고 토큰은 시작할 때 만든다. 그 값을 셸에 넘길 가장 단순한 길이다. stdout에는 이 줄만 쓰고 로그는 stderr로 보낸다 |
| 종료 신호 | 셸이 사이드카의 stdin을 닫으면 사이드카는 서버를 멈추고 끝낸다 | 셸이 갑자기 죽어도 파이프가 닫혀 신호가 간다. Windows에서 `SIGTERM`은 믿을 수 없다 |
| 프로세스 수명 | Windows Job Object(`KILL_ON_JOB_CLOSE`)에 셸을 넣는다. 정상 종료는 stdin 닫기, 느리면 `taskkill /T /F` | Tauri는 사이드카를 감독하지 않고 `kill()`은 직계만 끝낸다. 프로세스 트리는 Tauri → java → yt-dlp → ffmpeg이다 |
| 사이드카 실행 | `externalBin`을 쓰지 않는다. 번들한 런타임의 `java`를 Rust가 직접 실행한다 | `externalBin`은 `이름-<타깃 트리플>.exe` 단일 파일 규칙이라 JVM에 맞지 않는다 |
| 데이터 폴더 | 사이드카는 `--app-data <절대 경로>`를 반드시 받고 기본값이 없다 | `createServices`가 시작할 때 `<app-data>\work`를 통째로 지운다. 기본값이 사용자의 실제 폴더를 가리키면 실행 중인 다른 앱의 작업 폴더가 지워진다 |
| 가사용 JavaFX 웹뷰 | 1차에서는 그대로 둔다 | 3단계 이후 별도 작업(7단계) |
| `shared`의 순수 로직 | 3단계에서 정한다(후보: `js(IR)` 타깃의 얇은 파사드, 안 되면 TS 포팅 + 같은 케이스 표 테스트) | UI가 `FilenameFormatter`, `InputClassifier`, `ParsedInput`을 직접 쓴다 |
| UI 방향 | 시스템 글꼴, 시스템 테마(`color-scheme`), 기본 폼 컨트롤, 시맨틱 HTML. 커스텀 디자인 시스템을 만들지 않는다 | 불만이 입력·글꼴과 네이티브 느낌이지 디자인 자유도가 아니다(§5.2) |
| 프런트엔드 프레임워크 | 3단계에서 정한다. 0a·0b는 프레임워크 없이 `vanilla-ts` | 화면이 작다(컴포저블 약 560줄) |

### 2.1 다른 연동 패턴을 쓰지 않는 이유

- **Kotlin/Native C-FFI:** `engine`이 `java.nio`, `ProcessBuilder`, Ktor Netty, jsoup, JavaFX에 기대고 있다(`engine/build.gradle.kts`). Native로 가려면 사실상 다시 써야 한다.
- **JNI 임베딩(Rust 안에서 JVM 구동):** JVM이 Tauri와 같은 프로세스에서 돌아 크래시와 메모리 부족이 격리되지 않고, JVM 번들 크기는 그대로다. JavaFX 스레드(`Platform.exit`)와 Tauri의 메인 스레드가 한 프로세스에서 부딪힐 수 있다. 한 프로세스에서 JVM을 파괴한 뒤 다시 만들 수도 없다.
- **gRPC/stdio:** 지금의 HTTP + SSE 계약과 그 테스트를 버리고 새 계약을 만들 이유가 없다.

### 2.2 왜 프런트엔드가 서버에 직접 붙지 않는가

- `Guard.kt`가 `Origin` 헤더가 있는 요청을 모두 403으로 거부한다. Windows의 Tauri 웹뷰는 `fetch`에 항상 `http://tauri.localhost` Origin을 붙인다.
- 토큰 헤더 때문에 CORS preflight가 필요한데, 서버는 이를 처리하지 않는다. 브라우저의 `EventSource`는 커스텀 헤더를 보낼 수 없어서 SSE도 걸린다.
- 가드를 풀면(Origin 허용 목록 + CORS) 토큰이 웹뷰의 JS에 노출된다. Rust 브리지는 가드를 그대로 두고 토큰을 Rust 안에만 둔다.

## 3. 범위 밖 (YAGNI)

- 웹 배포, 코드 서명, 앱 자체 자동 업데이트, 다른 OS
- 가사 검색의 WebView2 전환(7단계에서 따로 검토)
- 기능 추가. 이 마이그레이션은 지금 동작을 그대로 옮긴다

## 4. 구조

```
[ 웹뷰: HTML/TS ] ── invoke / 이벤트 ── [ Tauri 코어: Rust ] ── HTTP + SSE (127.0.0.1, 토큰) ── [ 사이드카: JVM ]
                                                  │                                                  server → engine → shared
                                                  ├─ stdout 한 줄 = 시작 신호 (XGS-READY <port> <token>)
                                                  ├─ stdin 닫기 = 종료 신호
                                                  └─ Job Object = 셸이 죽으면 자손까지 정리
```

저장소 배치:

| 위치 | 내용 |
|---|---|
| `shared/`, `engine/`, `server/` | 그대로. 사이드카 진입점(`main`, 시작 신호, 부모 감시)은 `server/`의 `sidecar` 패키지에 둔다(설계 문서 §10.1 2단계 "main()만 분리") |
| `sidecar-host/` (새) | Rust 라이브러리 크레이트. 시작 신호 해석, 사이드카 시작·종료, Job Object, 토큰 달린 HTTP GET. **Tauri에 의존하지 않는다.** Tauri 크레이트는 첫 컴파일이 수 분 걸려서 이 로직의 테스트 루프를 느리게 하기 때문이다 |
| `shell/` (새) | Tauri 앱(프런트엔드 + `src-tauri`). `sidecar-host`를 경로 의존성으로 쓴다 |
| `app/` | Compose 앱. 6단계까지 남겨 두고 `run.bat`으로 계속 쓸 수 있다 |

## 5. 단계와 관문

| 단계 | 내용 | 끝났다는 증거 |
|---|---|---|
| 0a | **UI 프로토타입 (먼저):** 사이드카 없이 Tauri 웹뷰에 실제 화면을 가짜 데이터로 그려서 Compose와 나란히 비교한다. Rust 설치와 `shell/` 스캐폴드만 있으면 된다 | UI 관문 U1~U4 판정(§5.2) ([계획서](../plans/2026-10-10-tauri-ui-prototype.md)) |
| 0b | **스파이크:** 사이드카 진입점 + 최소 Tauri 셸. 시작·종료·정리·크기를 잰다 | 보고서 + **기술 관문 판정** ([계획서](../plans/2026-10-10-tauri-sidecar-spike.md)) |
| 1 | 사이드카 완성: `Diagnostics`(로그, 종료 기록, `last-run.txt`)를 `app`에서 옮기고 파일 로그를 쓴다. 번들한 JRE로 실행한다 | 사이드카만으로 로그·종료 기록이 지금과 같다 |
| 2 | Rust 브리지: 명령 8개와 SSE → 이벤트. 토큰을 Rust 안에 숨긴다 | 브리지 계약 테스트 |
| 3 | 프런트엔드 이식: `AppStateHolder` 논리와 `Labels`, 화면. `shared` 로직 재사용 방식 확정 | 지금의 `AppStateHolderTest` 시나리오가 새 테스트에서 통과 |
| 4 | 데스크톱 기능: 폴더 선택, 탐색기 열기, `settings.json`, 단일 인스턴스, 종료 연동 | README의 "알려진 제한" 항목과 동작이 같다 |
| 5 | 포장과 단일 exe: 번들 JRE + 셸. 이전 설계(§6.4)의 SFX 판정 방식 재사용 | 깨끗한 PC 흉내 검증 |
| 6 | `app/` 삭제, README·설계 문서 갱신 | `gradlew check` 통과 |
| 7 | (선택) 가사 검색의 JavaFX 웹뷰를 WebView2로 교체 | 구글 가사 통합 테스트 재검증 |

각 단계의 계획서는 앞 단계의 관문을 통과한 뒤에 쓴다. 0단계 결과가 1~5단계의 방식을 바꿀 수 있기 때문이다. 0a의 UI 관문이 통과하지 못하면 0b 이후는 하지 않는다(UI가 나아지지 않으면 마이그레이션이 줄 이득이 없다).

### 5.1 0b 기술 관문

**필수 (하나라도 실패하면 원인을 분석해 한 번 다시 시도하고, 그래도 실패하면 중단하고 Compose를 유지한다):**

| 번호 | 조건 |
|---|---|
| M1 | 셸이 사이드카의 시작 신호를 읽고, Rust에서 `GET /tools`가 200이다 |
| M2 | 창을 닫으면 3초 안에 사이드카 `java.exe`가 없다 |
| M3 | 셸을 강제 종료하면(`Stop-Process -Force`) 5초 안에 사이드카와 그 자손(`yt-dlp.exe`)이 모두 없다 |
| M4 | 웹뷰에서 서버로 직접 `fetch`하면 막힌다(가드가 그대로 유지됨을 확인하고, Rust 브리지가 필요함을 증명) |

**악화 한도 (동기가 UI 품질이므로 개선이 아니라 나빠지지 않는 선만 본다):**

| 항목 | 한도 (제안값, 사용자가 바꿀 수 있다) | 넘으면 |
|---|---|---|
| 창이 뜬 뒤 사이드카가 준비될 때까지(`waitedMs`, 3회 중앙값) | 10초 이하 | 사용자가 빈 화면이나 "준비 중"을 오래 보게 되어 UI 품질을 깎는다. 보고서에 적고 대응(시작 중 화면, 사이드카 미리 띄우기)을 정한 뒤 진행한다 |
| 100행 목록에 진행률을 초당 10회 갱신하면서 스크롤하고 입력해도 끊기지 않음 (0a 프로토타입에서 확인) | 눈으로 끊김이 없음 | 목록을 가상화하거나 갱신을 모은다 |
| 크기: 사이드카 `lib` 합계, Tauri 셸 exe, Compose 업 jar | 한도 없음, 기록만 | |
| 사이드카 시작 신호까지(`readyMs`), Job Object 생성 여부 | 기록만 | |

### 5.2 0a UI 관문

UI 품질이 동기이므로 사이드카보다 먼저 확인한다. 가짜 데이터(목록 100곡, 진행률이 움직이는 상태, 오류 문구가 있는 행)로 지금 화면을 웹뷰에 다시 그려서 Compose 화면과 나란히 놓고 본다.

사용자가 Compose 화면에서 아쉬워하는 점은 **한글 입력·글꼴**과 **네이티브 느낌**이다(디자인 자유도와 목록 성능은 아니라고 했다). 그래서 프로토타입은 커스텀 디자인을 만들지 않고 시스템 글꼴, 시스템 테마(`color-scheme`), 기본 폼 컨트롤, 시맨틱 HTML로 만든다. 웹뷰(WebView2)가 입력(Windows 텍스트 서비스)과 글꼴 렌더링(DirectWrite)을 운영체제 방식대로 처리하리라는 것이 이 마이그레이션의 가설이고, 0a는 그 가설을 확인한다.

| 번호 | 조건 | 확인 방법 |
|---|---|---|
| U1 | 사용자가 같은 상태의 두 화면을 나란히 보고 "Compose보다 낫다"고 판단한다 | 사용자의 눈. 같은 상태(빈 화면, 미리보기, 다운로드 중, 완료)를 캡처해서 비교한다 |
| U2 | **한글 입력:** 조합 중인 글자가 입력란에서 자연스럽다(조합 밑줄, 커서 위치). 붙여넣기, 드래그·더블클릭 선택, `Ctrl+A/C/V`, 우클릭 메뉴(잘라내기·복사·붙여넣기)가 된다 | 주소, 출력 폴더, 앨범명 입력란과 목록의 파일명으로 Compose와 같은 동작을 직접 해 본다 |
| U3 | **글꼴:** 한글·영문·숫자가 Compose보다 선명하고 시스템 글꼴(맑은 고딕, Segoe UI)로 그려진다. 현재 화면 배율에서 확인하고, 사용자가 배율을 바꿔 볼 수 있으면 125%, 150%도 본다 | 같은 위치를 확대한 캡처를 나란히 비교 |
| U4 | **네이티브 느낌:** 시스템 라이트·다크 설정을 따른다. `Tab` 순서가 자연스럽고 `Enter`로 조회된다. 키보드만으로 조회부터 다운로드 시작까지 할 수 있다. Narrator(`Win+Ctrl+Enter`)가 버튼과 입력란의 이름을 읽는다 | 직접 조작 |

한 항목이라도 통과하지 못하면 그 이유를 적고 사용자가 계속할지 정한다. U1은 사용자의 판단이라 U2~U4가 모두 통과해도 U1이 아니면 중단한다.

## 6. 위험

| 위험 | 대응 |
|---|---|
| 화면이 기대만큼 나아지지 않는다. 이 마이그레이션의 유일한 이득이 UI 품질이므로 이것이 가장 큰 위험이다 | 0a에서 사이드카 없이 먼저 확인한다. 통과하지 못하면 0b 이후를 하지 않는다 |
| 단일 exe: Tauri의 `resources`는 exe에 내장되지 않는다. Enigma Virtual Box는 자식 프로세스(`java.exe`)가 가상 파일 시스템을 못 볼 수 있다 | 5단계에서 풀어서 실행하는 SFX를 기본 후보로 두고 측정으로 정한다 |
| WebView2 런타임: Windows 11에는 있지만 Windows 10은 따로 설치해야 한다 | 5단계에서 "설치 없는 exe" 목표와 조율한다 |
| 로그 위치: 지금은 `jpackage.app-path`를 기준으로 `log\`를 정한다 | 1단계에서 사이드카용 규칙을 정하고 README를 고친다 |
| `settings.json`을 쓰는 곳이 둘이 되면 충돌한다 | 4단계에서 쓰는 주체를 한 곳으로 정한다 |
| JavaFX가 JVM을 붙잡아 종료가 안 된다 | 사이드카는 `exitProcess`로 끝내고 `FxWebViewBrowser.close()`는 서버 scope가 끝날 때 불린다 |
| Rust 코드를 계획 작성 시점에 컴파일해 보지 못했다(이 PC에 Rust가 없음) | 0단계 Task 4에서 처음 컴파일한다. 오류가 나면 계획의 시그니처와 테스트를 기준으로 고친다 |

## 7. 문서 갱신

5~6단계에서 README의 "구조", "실행", "문제가 생겼을 때"(로그 위치)와 이 문서의 §4 기술 스택·모듈 구조를 고친다. 0단계에서는 문서를 건드리지 않고 보고서만 남긴다.
