## 막힌 점과 고친 것

- **작업 순서를 바꿨다.** Task 5(크레이트 둘을 내려받음)는 계획에 따라 사용자의 허락이 필요해서, 허락을 받기 전에 TypeScript만 건드리는 Task 6·7을 먼저 했다. 인터페이스는 이름(문자열)뿐이라 순서가 결과에 영향을 주지 않았다. 허락은 받았고 Task 5~9는 계획의 순서로 했다.
- 계획을 쓰며 겪은 것(계획서의 "Global Constraints"에 반영돼 있다): 시작 직후 닫기가 10번 중 9번 "실패"한 것은 제품이 아니라 확인 스크립트가 `Process.MainWindowHandle`로 창을 찾은 탓이었다. 단일 인스턴스 플러그인이 시작하자마자 보이는 숨은 창을 만들어서 처음 몇십 ms 동안은 그것이 주 창으로 잡힌다. 스크립트는 이제 클래스 `Tauri Window`인 창을 찾는다. 시스템 대화상자에 글자를 넣는 방법(`WM_SETTEXT`, 값 패턴, `SendKeys`)은 쓸 수 없거나 위험해서(포커스가 다른 창이면 거기에 입력된다) 목록에서 하위 폴더를 고르는 방식으로 했다.
- 사이드카 시작을 `Builder` 앞에서 `build()` 뒤로 옮겼다(계획의 결정). 옮기지 않으면 두 번째 실행도 사이드카를 띄워 첫 실행의 `work\`를 지운다. 계획을 쓰며 단일 인스턴스가 없는 3단계 빌드로 확인했다: 두 번째 실행이 15초 넘게 살아 있고 사이드카가 둘이 되며 첫 실행의 `work\` 표식이 사라지고 첫 창은 최소화된 채였다.

## 최종 리뷰 뒤 고친 것

전체 브랜치를 새 맥락의 리뷰어(opus)가 한 번 읽었다. Critical은 없었고 Important 하나와 Minor 아홉이었다. 지적을 하나하나 확인해 사실인 것은 먼저 실패하는 시험이나 재현으로 보이고 고쳤다.

- **Important: 점검 도구가 사용자의 실행 중인 앱과 부딪힌다.** 미끼 셸(사용자의 앱 흉내)을 띄워 두고 재현했다: 점검용 빌드가 일반 빌드와 같은 `identifier`라서 단일 인스턴스 뮤텍스를 공유해 점검 사본이 "두 번째 실행"으로 즉시 끝나고(미끼의 창을 앞으로 가져온다), 스크립트의 `Get-Sidecar`가 이 PC의 모든 사이드카를 보아 미끼의 사이드카를 20초 기다리고, 복구 줄(`Get-Process shell | Stop-Process`)은 사용자의 앱을 끝낼 수 있었다. 고친 것: `check.conf.json`에 `identifier`를 `com.xgetsongs.shell.check`로 줘 뮤텍스와 WebView2 프로필을 나눴고, `Get-Sidecar`를 앱 데이터가 `xgs-bridge-check-*`인 사이드카로 좁혔고, 이름으로 `shell`·`vite`를 모두 끝내는 명령을 없앴다(자기가 띄운 PID와 이 저장소의 vite만). 미끼가 떠 있는 채로 시작 직후 닫기 3번, 설정 확인, 탐색기 확인이 독립적으로 통과했고 미끼와 그 사이드카는 그대로였다.
- **`탐색기에서 보기`가 쉼표가 든 폴더를 열지 못한다.** `explorer.exe`는 명령줄을 쉼표에서 나누고 `Command::arg`는 공백이나 탭이 없는 경로에 따옴표를 붙이지 않는다. 쉼표가 든 폴더(`Hits,2020`)를 따옴표 없이 열면 `Documents`가 열렸다(직접 재현). 항상 따옴표를 붙여 넘긴다(`explorer_argument`, 시험 하나). 종단 확인도 쉼표가 든 폴더로 바꿨다: 옛 빌드로는 FAIL(창이 안 열림), 새 빌드로는 PASS(1,342ms).
- **폴더 선택 단추의 더블클릭이 대화상자를 둘 연다.** 시스템 대화상자는 뜨는 데 시간이 걸리고 그때서야 창을 잠근다. 한 번에 하나만 열도록 했다(시나리오 G: 고치기 전에는 두 번 선택돼 `…폴더 2`, 고친 뒤 `…폴더 1`).
- **설정 파일의 따옴표 친 불리언(`"overwrite":"true"`)**을 Compose(kotlinx.serialization)는 읽는데 포트는 파일 전체를 못 쓰는 파일로 보고 기본값으로 돌아갔다(손으로 고친 파일에서 첫 변경이 저장된 폴더를 덮어쓴다). 소문자 `"true"`·`"false"`를 읽는다(시험 하나. 리뷰어가 kotlinx 소스에서 확인한 것을 근거로 했고 이쪽에서 따로 확인하지는 않았다. 틀렸더라도 읽는 범위가 넓어질 뿐이다).
- **상대 경로의 출력 폴더는 대화상자의 시작 폴더가 되지 못했다**(대화상자는 상대 경로를 받지 못한다. Kotlin의 `File`은 작업 폴더에 대해 풀었다). 절대 경로로 바꿔 넘긴다(시험 하나).
- **확인 도구의 구멍 둘:** (1) 설정 확인은 닫기 협의가 깨져도(페이지가 응답하지 않아도 0.4초 저장 타이머가 파일을 쓴다) 통과했다. 이제 셸이 1.5초 안에 끝나는지(닫기 요청에 페이지가 답했는지)를 판정에 넣었고(882~1,028ms), 페이지가 부르는 명령 이름과 닫기 이벤트 이름이 셸의 것과 같은지를 시험한다(`rust-names.test.ts`: 이름을 하나 바꾸면 실패). (2) Rust 포트의 원본 이름 점검은 `#[ignore]`나 주석 처리된 함수, 시험이 아닌 함수도 세었다. 이제 `#[test]`가 있고 `#[ignore]`가 아닌 함수만 센다(변형 둘이 잡혔다).
- **`tauri-plugin-dialog`의 초기화 스크립트는 모든 페이지의 `window.alert`와 `window.confirm`을 이 앱이 허용하지 않는 명령 호출로 바꾼다**(`alert()`는 아무 일도 안 하고 `confirm()`은 프로미스를 돌려준다). 지금 쓰는 곳은 없고 나중 코드의 함정이라 `lib.rs`에 주석을 남겼다.
- **알려진 한계로 남긴 것(리뷰의 Minor 둘):** 단일 인스턴스 뮤텍스는 `RunEvent::Exit`에서 풀려 사이드카가 멈추기 전이므로, 닫자마자(0.5~3초 안에) 다시 열면 앞 사이드카가 멈추는 동안 새 사이드카가 `work\`를 지운다(앞 작업은 어차피 취소되는 중이고 영향은 `last-run.txt`와 `sidecar-stderr.log`가 섞일 수 있는 정도다). 종료를 `ExitRequested`로 옮기면 뮤텍스는 지키지만 닫는 동안 다시 열어도 아무것도 안 뜬다. 또 `탐색기에서 보기`가 띄운 `explorer.exe`는 셸의 Job 안에 있어서, 이미 떠 있는 탐색기에 폴더를 넘기고 끝나는 짧은 순간(수십 ms)에 앱을 닫거나 탐색기가 "폴더 창을 별도 프로세스로 열기"로 설정돼 있으면 창이 사라질 수 있다(종단 확인은 창이 앱보다 오래 남음을 보였다).
- 리뷰 뒤 같은 확인을 새 빌드로 다시 돌렸다: 화면 점검 `waitedMs` 1,083ms·영상 한 곡 6,256ms·취소 638ms, 시작 직후 닫기 10번 2,916~3,278ms 모두 `reason=user`·실패 0, 강제 종료 175 / 186 / 187ms, 단일 인스턴스 151ms, 멈춘 페이지 2,131ms, 폴더 선택 창 PASS.

## 사용자가 직접 확인할 것

- **먼저 Compose 앱을 끈다.** 셸은 이제 같은 앱 데이터 폴더(`%APPDATA%\xGetSongs`)를 쓰고 사이드카는 시작할 때 그 안의 `work\`를 지운다.
- 일반 빌드(`npm run tauri build -- --no-bundle`)를 만들어 `XGS_SIDECAR_DIR=<저장소>\server\build\sidecar-image`를 주고 `shell\src-tauri\target\release\shell.exe`를 실행한다. 사용자의 yt-dlp와 `settings.json`(출력 폴더, 옵션)이 그대로 쓰인다.
- 한글 입력: 주소, 출력 폴더, 앨범명, **순위 번호** 칸(영상 한 곡을 조회하면 나온다).
- `폴더 선택`: 창이 앱 위에 모달로 뜨고 현재 폴더에서 시작하는지, 취소하면 그대로인지.
- `탐색기에서 보기`: 다운로드 중에도 눌리는지, 아직 없는 하위 폴더면 가장 가까운 폴더를 여는지.
- 옵션을 바꾼 직후 창을 닫고 다시 열어 기억하는지(Compose 앱과 같은 파일).
- 앱을 두 번 실행하면 두 번째는 사라지고 첫 창이 앞으로 오는지(최소화해 둔 채로도).
- yt-dlp 설치·업데이트 버튼(실제로 한 번도 불러 보지 못했다).
- 폴더 선택 창이 닫힌 뒤에 페이지를 클릭하지 않고도 키보드가 먹는지.
- 이름에 쉼표가 든 폴더(`Hits,2020`)에서 `탐색기에서 보기`.

## 이 단계가 확인하지 않은 것

- 첫 창의 숨은 창이 만들어지기 전(시작 직후 수십 ms)의 거의 동시 실행: 플러그인은 그때 두 번째 실행을 끝내지 않고 둘 다 뜬다(플러그인 소스에서 확인했고 시험하지 않았다).
- Compose 앱과 셸을 동시에 실행하는 경우(Compose 앱에는 단일 인스턴스가 없어 막을 수 없다).
- 사용자의 실제 `%APPDATA%\xGetSongs`에서의 실행(확인은 임시 폴더로 했다. `settings.json`은 실제 파일의 복사본으로 읽기만 확인했다).
- 폴더 선택 창에서 경로를 직접 입력하는 경우, 네트워크 드라이브·존재하지 않는 드라이브.
- 점검용 빌드와 일반 빌드는 같은 `target\release\shell.exe`를 덮어쓴다(점검 뒤에 일반 빌드를 다시 만든다).
- 사용하지 않는 `tauri-plugin-opener`와 `opener:default` 권한이 남아 있다(웹뷰가 시스템의 기본 앱으로 URL을 열 수 있다. 5단계 전에 정리한다).
- `sidecar-host`의 `job.rs:11` clippy 경고 하나(2단계부터 있던 것이며 이 단계가 만든 것이 아니다).
- 점검 실행은 한 번이다. 시간 값은 반복 측정이 아니다.
- 2~3단계에서 넘어온 항목: 사이드카가 실행 중에 죽는 경우, 999곡 목록의 성능, 우클릭 새로고침, `install_yt_dlp`·`update_yt_dlp`의 실제 호출.
