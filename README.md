# xGetSongs

YouTube 재생목록 ID를 입력하면 목록의 모든 영상에서 오디오를 추출해 m4a로 저장하고, 영상 주소 1개를 입력하면 그 영상의 오디오만 m4a로 저장하는 Windows 데스크톱 앱입니다. 화면은 Tauri(웹뷰)가 그리고, 다운로드와 태그 같은 일은 Kotlin으로 만든 서버(사이드카)가 합니다. 나중에 웹으로 옮길 수 있게 설계했습니다.

오디오는 YouTube의 AAC 원본(약 130kbps, itag 140)을 재인코딩 없이 그대로 저장합니다. 음질이 좋아지는 방식은 아니고 원본 그대로라는 뜻입니다.

파일명 형식: `{순위번호 001~999} {가수명} - {제목}.m4a`

예: `001 소연 (SOYEON) - 퇴사할게여 (Narr. 기안84).m4a`

앱의 "파일명에 순번 포함" 옵션을 끄면 `{가수명} - {제목}.m4a`로 저장합니다(기본은 켜짐이고, 트랙 번호는 옵션과 상관없이 순위입니다). 순번이 없으면 한 재생목록에서 같은 가수와 제목의 영상이 같은 파일명이 될 수 있어서, "기존 파일 덮어쓰기"가 꺼져 있으면 하나만 저장하고 나머지는 건너뛰며 켜져 있으면 마지막에 끝난 것으로 덮어씁니다.

설계 문서: [docs/superpowers/specs/2026-10-04-xgetsongs-design.md](docs/superpowers/specs/2026-10-04-xgetsongs-design.md) (처음 설계, 화면이 Compose였을 때), 화면을 Tauri로 옮긴 설계: [docs/superpowers/specs/2026-10-10-tauri-kotlin-sidecar-design.md](docs/superpowers/specs/2026-10-10-tauri-kotlin-sidecar-design.md)

## 저장 위치

- 재생목록: 출력 폴더 안에 재생목록 이름의 폴더를 만들어 그 안에 저장합니다. 예: `D:\Music\내 재생목록\001 가수 - 제목.m4a`. 폴더 이름의 금지 문자(`\ / : * ? " < > |`)는 전각 문자로 바꾸고 80자로 줄이며, 이름이 비면 `재생목록`을 씁니다. 같은 이름의 재생목록은 같은 폴더를 씁니다.
- 영상 1개: 폴더를 만들지 않고 출력 폴더에 바로 저장합니다.
- 폴더 이름은 앨범명 입력란 하나로 정합니다. 조회하면 재생목록 제목이 채워지고(영상 1개는 비어 있음), 다른 이름을 쓰면 재생목록이든 영상 1개든 출력 폴더 안의 그 이름의 폴더에 저장하며 그 이름이 모든 파일의 앨범 태그가 됩니다(폴더 이름은 금지 문자 처리, 80자 제한, 빈 이름은 `재생목록`으로 위의 규칙과 같고, 태그에는 입력한 원문을 씁니다). 고치지 않거나 비우면 위의 기본 동작 그대로입니다(앨범 태그도 폴더와 같은 재생목록 제목).

목록을 조회하면 앱의 출력 폴더 입력란 아래에 실제 저장 위치가 표시되고, 그 줄 오른쪽의 `탐색기에서 보기` 버튼으로 그 폴더를 탐색기에서 열 수 있습니다(폴더가 아직 없으면 가장 가까운 상위 폴더를 엽니다).

## 태그

받은 m4a마다 MP4 태그를 씁니다(재인코딩 없음, 텍스트는 UTF-8). 이전 버전의 앱이 받은 mp3 파일은 그대로 두고 다시 쓰지 않습니다. 값은 파일명과 달리 금지 문자를 바꾸거나 길이를 줄이지 않은 원문이고, 예외는 ffmpeg의 메타데이터 파일 형식 때문에 값 끝의 `\`를 전각 `＼`로 바꾸고 줄바꿈과 탭을 뺀 제어 문자를 지우는 것뿐입니다.

- 제목: 파싱한 제목
- 가수: 파싱한 가수
- 앨범 아티스트: 모든 곡에서 `Various Artists`
- 앨범: 앨범명 입력란에는 조회하면 재생목록 제목이 채워지는데, 이 칸을 고치지 않거나 비우면 기본 동작 그대로입니다. 칸을 고쳐 쓰면 모든 곡에 그 이름을 쓰고(영상 자체의 앨범이 있어도, 영상 1개에도) 폴더 이름도 그 이름이 되며, 가사 검색에는 그 이름 대신 영상 자체의 앨범을 씁니다. 기본 동작은 폴더 이름과 같은 재생목록 제목입니다(영상 자체의 앨범이 있어도). 영상 1개는 폴더가 없으니 영상 자체의 앨범(YouTube가 앨범 정보를 알고 있을 때, yt-dlp의 `album`)을 쓰고, 그것도 없으면 쓰지 않습니다.
- 트랙 번호: 순위
- 주석: 영상 URL
- 가사: 영상 설명란에 `[Lyrics]`나 `가사`처럼 제목만 있는 줄이 있으면 그 아래 가사를 가사 태그에 씁니다. 구분선(`=====`), 링크, 저작권, 해시태그, `[Rom]`이나 `(English)` 같은 다른 구역 제목 줄 앞까지이고, 처음 나온 가사 구역 하나만 씁니다. 가사 제목이 없거나 가사가 3줄이 안 되면 설명란에서는 가사를 찾지 못한 것입니다(아래 "가사 검색").
- 커버: 썸네일의 가운데를 정사각형으로 잘라 넣습니다 (썸네일이 없으면 커버 없이 태그만 씁니다)

태그를 쓰지 못하면 그 항목은 실패로 처리되며 "실패 항목 재시도" 버튼으로 다시 받을 수 있습니다.

### 가사 검색

가사는 영상 설명란에 `[Lyrics]`나 `가사` 구역이 있으면 거기서 가져오고, 없으면(옵션이 켜져 있을 때, 기본) 공개 가사 데이터베이스 LRCLIB(lrclib.net)에서 아티스트, 제목, 앨범, 길이로 찾아 씁니다. 제목과 아티스트가 맞고 길이 차가 8초 이하인 결과만 쓰고(일본어판·라이브·리믹스 같은 다른 버전은 제외), 서비스가 응답하지 않거나 요청이 너무 많다고 하면 5분 동안 검색을 쉬며, 둘 다 못 찾으면 가사 태그를 쓰지 않으므로 파일에 가사가 남지 않습니다. 이 검색은 아티스트, 제목, 앨범, 길이 네 값을 lrclib.net으로 보내므로, 보내고 싶지 않으면 옵션의 `가사가 없으면 인터넷에서 검색` 체크를 끄세요(그러면 설명란에 가사가 있는 곡만 가사가 들어갑니다). 목록의 완료된 각 행에는 가사 결과가 `가사 ✓ 설명란`, `가사 ✓ 인터넷`, `가사 없음`(찾아 봤지만 없음), `가사 없음 (검색 끔)` 중 하나로 함께 표시됩니다. 가사는 저작물이므로 개인 사용 목적으로만 쓰세요.

LRCLIB에도 없으면 구글 검색 결과의 가사 카드에서 가져옵니다(같은 옵션이 켜져 있을 때만). 앱 안에 보이지 않게 숨겨 둔 WebView2 창(시크릿 모드)으로 `가수 제목 lyrics`를 검색하고, 가사 카드의 줄을 문단 단위로 읽습니다. 이때 아티스트와 제목이 구글로 보내집니다(WebView2 기본 User-Agent(Edge) 그대로, 쿠키와 캐시는 창을 닫으면 사라짐). 구글 호출은 곡당 1회(아티스트 이름에 괄호 병기가 있고 카드가 없으면 괄호를 뗀 이름으로 1회 더)이고 호출 사이에 10초 이상 간격을 두며, CAPTCHA·동의창·429·시간 초과가 나오면 우회하지 않고 5분, 10분, 20분…(최대 60분) 동안 구글 검색을 쉽니다. 같은 곡의 결과는 앱을 켜 두는 동안 기억해 다시 묻지 않습니다. 구글 카드는 곡의 버전(일본어판, 라이브 등)을 알려 주지 않아 다른 버전의 가사가 섞일 수 있습니다. 구글이 가사 카드의 마크업을 바꾸면 이 단계는 조용히 실패하고 로그에 `카드는 있으나 줄을 읽지 못함`이 남습니다. 구글 약관은 자동 질의를 사실상 금지하고 가사는 저작물이므로 개인 용도로만 쓰세요. 배포하거나 서비스로 넓힌다면 Musixmatch 같은 정식 API로 바꿔야 합니다.

## 필요한 것

받은 `xGetSongs.exe`를 쓰는 PC에 필요한 것:

| 도구 | 용도 | 설치 |
|---|---|---|
| yt-dlp | 영상에서 오디오 추출 | 앱의 "yt-dlp 설치" 버튼 또는 `winget install yt-dlp.yt-dlp` |
| ffmpeg | 태그와 커버 쓰기, 썸네일 변환 | `winget install Gyan.FFmpeg` |
| Node.js 22+ 또는 Deno 2.3+ | yt-dlp가 YouTube를 읽는 데 필요 | `winget install OpenJS.NodeJS` |
| Microsoft Edge WebView2 런타임 | 창을 그린다 | Windows 11과 업데이트된 Windows 10에는 들어 있다. 없으면 앱이 안내한다 |

Java는 필요 없습니다(exe 안에 들어 있습니다). 앱 첫 화면 위쪽에서 yt-dlp, ffmpeg, Node.js(또는 Deno)의 설치 여부와 버전을 확인할 수 있습니다.

소스에서 exe를 만드는 PC에는 JDK 21(Gradle과 서버), Node.js 22.18 이상(화면과 화면 시험), Rust와 Windows용 C++ 빌드 도구(MSVC 링커와 Windows SDK: Visual Studio Build Tools의 "C++를 사용한 데스크톱 개발")가 필요합니다.

## 실행

```powershell
.\run.bat    # dist\xGetSongs.exe를 실행합니다(없으면 package-exe.bat으로 먼저 만듭니다)
```

소스를 고친 뒤에는 `.\package-exe.bat`으로 exe를 다시 만드세요(아래 "하나의 exe로 묶기"). 앱은 마지막에 쓴 옵션(출력 폴더, 덮어쓰기, 파일명에 순번 포함, 가사 인터넷 검색)을 `%APPDATA%\xGetSongs\settings.json`에 저장해 두었다가 다음 실행에 되살리며, 입력한 주소, 영상 1개의 순위 번호, 앨범명(폴더명)은 기억하지 않습니다.

동시에 받는 곡 수는 고르지 않고 서버가 정합니다. 이 컴퓨터의 프로세서(논리 코어) 수의 70%이고, 소수점은 버리며 최소 1개입니다(프로세서 12개이면 8개, 4개이면 2개). 작업 로그의 `concurrency=`에 실제로 쓴 수가 남습니다. 예전 `settings.json`에 있던 `concurrency` 값은 무시합니다.

작업이 끝나면(취소와 중단도 포함) 버튼 줄에 `완료 — 성공 8 · 건너뜀 0 · 실패 1 · 소요 3분 05초`처럼 결과와 걸린 시간을 보여 줍니다. 시간은 `다운로드 시작`(또는 `실패 항목 재시도`)을 누른 때부터 작업이 끝났다는 신호가 올 때까지이고, 서버와의 연결이 끊겨 끝난 경우에는 보여 주지 않습니다.

## 테스트

```powershell
.\gradlew.bat check                     # Kotlin 단위 테스트 (shared, diagnostics, engine, server)
.\gradlew.bat :engine:integrationTest   # 실제 yt-dlp, YouTube, LRCLIB, 구글 가사 카드를 쓰는 통합 테스트 (도구가 없거나 서비스가 응답하지 않으면 건너뜀)
.\gradlew.bat :server:sidecarImageTest  # 만든 사이드카 이미지(번들 런타임)로 서버를 실제로 띄워 보는 시험

cargo test --manifest-path sidecar-host\Cargo.toml   # Rust: 사이드카 제어, 브리지, 설정 파일, 묶은 exe 풀기 (Tauri 없이 빠르게 돈다)
cd shell
node --test "tests/*.test.ts"            # 화면 로직
npx tsc --noEmit                         # 화면의 타입 검사
```

`cargo test`가 건너뛰는 시험 둘은 실제 서버를 상대로 합니다(`#[ignore]`: 가짜 서버가 진짜와 어긋나지 않았는지 보는 것입니다):

```powershell
$env:XGS_SIDECAR_DIR = "$PWD\server\build\sidecar-image"   # 먼저 .\gradlew.bat :server:sidecarImage
cargo test --manifest-path sidecar-host\Cargo.toml --test real_sidecar -- --ignored   # 2초: 도구 상태, 오류 문구, 인증 거부, 종료 기록
```

`real_download`는 실제 yt-dlp·ffmpeg·인터넷으로 영상 하나를 조회하고 한 곡을 받고 작업 하나를 취소합니다(조회·진행 이벤트의 필드 모양을 실제 서버와 대조하는 시험은 이것뿐입니다). 필요한 환경 변수는 `sidecar-host/tests/real_download.rs`의 맨 위에 있습니다.

화면과 셸을 개발하는 방법(환경 변수, 점검 페이지, 가짜 서버로 화면만 보기)은 [shell/README.md](shell/README.md)에 있습니다.

## 하나의 exe로 묶기 (Tauri 셸)

```powershell
.\package-exe.bat
```

`dist\xGetSongs.exe` 한 파일(약 86MB)이 만들어집니다. Tauri 셸의 exe 뒤에 사이드카 이미지(Kotlin 서버와 그것을 돌리는 Java 런타임)를 붙인 것이라 이 파일만 복사해 가면 됩니다. 만드는 PC에는 JDK 21, Node.js, Rust가 필요하고 받는 PC에는 필요 없습니다.

- 처음 실행하면 런타임을 `%LOCALAPPDATA%\xGetSongs\runtime\<해시>`에 풀기 때문에 사이드카가 준비되기까지 4~5초 걸립니다(창은 바로 열립니다). 다음 실행부터는 그 폴더를 그대로 써서 1초쯤 걸립니다. 이 폴더는 지워도 다시 풀리는 캐시이고(파일이 깨졌거나 `java.exe`가 없어졌으면 스스로 다시 풉니다), exe를 새 빌드로 바꾸면 옛 폴더는 다음 실행에서 지웁니다.
- 로그는 `%APPDATA%\xGetSongs\logs`에 남습니다(exe 옆에 폴더를 만들지 않습니다).
- 창을 여는 데 Microsoft Edge WebView2 런타임이 필요합니다. Windows 11과 업데이트된 Windows 10에는 들어 있고, 없으면 안내 상자가 뜨며 [확인]을 누르면 설치 프로그램을 받는 페이지를 엽니다.
- 서명하지 않은 파일이라 내려받은 뒤 처음 실행할 때 Windows SmartScreen이 경고할 수 있습니다. 아이콘은 Tauri의 기본 아이콘입니다.
- yt-dlp, ffmpeg, Node.js(또는 Deno)가 필요한 점은 위 "필요한 것"과 같습니다.

## 문제가 생겼을 때

앱이 갑자기 사라지거나 멈췄다면 원인이 아래 파일에 남아 있을 수 있습니다. 로그는 서버(사이드카)가 씁니다.

- **로그:** 묶은 exe(`dist\xGetSongs.exe`)는 `%APPDATA%\xGetSongs\logs\xgetsongs.log`에 씁니다(`XGS_SIDECAR_APPDATA`로 앱 데이터 폴더를 바꿨다면 그 폴더의 `logs`). 환경 변수(`XGS_SIDECAR_DIR`, `XGS_SIDECAR_LIB`)나 exe 옆의 `sidecar` 폴더로 사이드카를 찾아 띄운 셸(개발)은 셸 exe 옆의 `log`에 씁니다. 어느 쪽이든 `XGS_SIDECAR_LOGDIR`이 있으면 그 폴더입니다. 정한 폴더를 만들 수 없으면 앱 데이터 폴더의 `logs`에, 거기도 안 되면 `%TEMP%\xgetsongs-logs`에 씁니다. 실제로 쓰는 폴더는 로그의 시작 정보 `로그 폴더:` 줄에 있습니다. 날짜와 5MB 단위로 나뉘고(`xgetsongs.2026-10-07.0.log`처럼) 7일, 합계 50MB까지 보관합니다. 한 줄마다 바로 기록하므로 강제 종료돼도 마지막 줄이 남습니다. 시작 정보(Java, OS, 메모리, 도구 경로), 작업 시작과 옵션, 항목별 완료·건너뜀·실패와 사유, 작업 요약, 취소, 이벤트 연결이 끊긴 일(앱이 서버를 멈추는 중의 끊김은 제외), 처리되지 않은 예외를 적고, 토큰, 요청 헤더, 가사, 영상 제목과 파일 이름은 적지 않으며 오류 문구 속의 파일 경로와 파일 이름도 `<경로>`, `<파일명>`으로 가립니다. 파일에는 앱 자신의 DEBUG 줄(항목 시작 등)도 들어 있습니다.
- **`sidecar-stderr.log`:** `%APPDATA%\xGetSongs`에 있습니다. 서버가 표준 오류로 쓴 것을 셸이 받아 적은 파일입니다. 로그 설정이 읽히기 전의 오류나 서버가 뜨지 못한 이유가 여기에만 남을 수 있습니다. 앱을 시작할 때마다 새로 쓰니, 문제가 생겼으면 다시 실행하기 전에 복사해 두세요.
- **`hang-날짜-시각.txt`:** 로그와 같은 폴더에 생기는 파일입니다. 서버의 작업 스레드가 5초 넘게 응답하지 않으면 모든 스레드가 그때 무엇을 하고 있었는지와 메모리·GC 정보를 여기에 저장하고 로그에도 ERROR로 남깁니다(창 자체가 멈춘 것은 기록하지 않습니다). 멈춤이 이어지면 같은 파일에 덧붙이되 간격을 30초, 60초, 120초…로 늘려 최대 30분으로 하고(로그에는 그때마다 한 줄만), 파일이 5MB에 이르면 `이후 덤프는 생략함(파일 크기 제한)` 한 줄을 쓰고 더 덧붙이지 않습니다. 다시 응답하면 로그에 `서버 스레드 응답 회복 (총 N초)`를 적습니다. 파일은 20개까지 보관합니다. 절전에서 깨어난 경우처럼 확인 주기가 크게 벌어진 때는 멈춤으로 보지 않습니다.
- **`JVM 종료 시작` 줄:** 서버가 종료되기 시작할 때마다 로그에 남습니다. 창의 닫기 버튼을 눌렀다면 그 앞쪽에 `사용자가 창 닫기를 요청함`과 `내장 서버 정지`가 있고 이 줄은 `사용자가 창을 닫음`이라고 적힙니다. `창을 닫지 않은 종료`(WARN)라고 적혀 있으면 사용자가 창을 닫지 않았는데 끝나기 시작한 것입니다(SIGTERM, 로그오프·시스템 종료, 또는 처리되지 않은 예외 뒤의 종료). 직전에 처리되지 않은 예외가 있었으면 `직전에 처리되지 않은 예외가 있었음`이 붙습니다. 그 줄에 종료 시점의 가동 시간, 서버에 등록된 작업 수(끝났어도 이벤트를 아직 받아 가지 않은 작업을 포함), 힙 사용량이 같이 적힙니다. 이 줄조차 없이 로그가 끊겼다면 작업 관리자의 강제 종료나 크래시처럼 종료 처리를 거치지 않은 경우입니다. 셸이 갑자기 끝났을 때도 대개 이렇습니다: 셸이 끝나면 Windows가 서버도 함께 끝내기 때문에 종료 기록을 쓸 틈이 없고, 다음 실행의 로그에 아래 `last-run.txt`의 경고가 남습니다.
- **`last-run.txt`:** 로그와 같은 폴더에 서버가 시작할 때 `state=running`으로 적고 종료 처리를 거치면 `state=exited`로 고치는 작은 파일이며, 다음 실행이 시작할 때 `state=running`인 채 남아 있으면 로그에 `이전 실행(PID …, 시작 …)이 정상 종료 기록 없이 끝났음: 강제 종료, 크래시, 전원 차단 등의 가능성` 경고를 남깁니다(그 프로세스가 아직 살아 있으면 대신 `다른 실행이 아직 실행 중임 (PID …)`).
- **화면에 `서버를 시작하지 못했습니다: …`가 보일 때:** 뒤의 문구가 이유입니다. `런타임을 풀지 못했습니다`나 `자리에 놓지 못했습니다`이면 exe가 자기 안의 Java 런타임을 `%LOCALAPPDATA%\xGetSongs\runtime`에 풀지 못한 것입니다(디스크가 가득 찼거나 폴더를 쓸 수 없음, 백신이 막음). 그 폴더를 지우고 다시 실행해 보세요(지워도 다시 풀립니다). `checksum`이 보이면 exe 파일이 복사 중에 깨진 것이니 다시 복사하세요.

문제를 알릴 때는 가장 최근의 `xgetsongs.log`(그리고 `hang-*.txt`, `sidecar-stderr.log`가 있으면 그것도)를 함께 보내 주세요. 로그에는 출력 폴더와 앱 폴더의 경로가 들어 있지만 곡 제목과 파일 이름은 없습니다.

## 구조

```
shared/        순수 Kotlin: 입력 판별, 제목 파싱, 파일명 생성, API 모델
engine/        yt-dlp·ffmpeg 호출, 재생목록 조회, 다운로드 작업 관리, 출력 저장소, 가사 검색(LRCLIB, 구글 가사 카드)
server/        Ktor API 서버와 사이드카 진입점 (127.0.0.1에만 열리고 실행할 때마다 새 토큰이 있어야 접근)
diagnostics/   로그 설정, 종료 기록, last-run.txt, 멈춤 감시
sidecar-host/  Rust 라이브러리: 사이드카 시작·종료, 서버 호출과 이벤트(브리지), settings.json, 폴더 열기, 묶은 exe 안의 런타임 풀기, xgs-pack
shell/         Tauri 앱: 화면(TypeScript)과 창을 여는 Rust 셸
```

화면(웹뷰)은 서버에 직접 붙지 않고 Rust 셸의 명령(`invoke`)만 부릅니다. 셸이 서버의 HTTP·SSE를 대신 부르고, 서버의 토큰은 셸 안에만 있습니다. 설계: [docs/superpowers/specs/2026-10-10-tauri-kotlin-sidecar-design.md](docs/superpowers/specs/2026-10-10-tauri-kotlin-sidecar-design.md).

## 알려진 제한

- 음질은 YouTube의 AAC 원본(약 130kbps)을 그대로 쓰며 고를 수 없습니다. m4a를 읽지 못하는 오래된 기기에서는 재생되지 않고, 예전 버전처럼 mp3로 받는 방법은 없습니다. 이전 버전이 받은 mp3 파일은 건드리지 않으며, 같은 곡을 다시 받으면 덮어쓰지 않고 `.m4a`가 옆에 따로 생깁니다. YouTube가 m4a 오디오를 주지 않는 영상은 "m4a 오디오 형식이 없습니다."로 실패하고 "실패 항목 재시도"로 다시 받을 수 있습니다.
- 재생목록의 모든 곡이 "m4a 오디오 형식이 없습니다."로 실패하면 영상 문제가 아니라 yt-dlp가 낡았거나 JavaScript 런타임(Node.js, Deno)에 문제가 있는 것일 수 있습니다. 앱 위쪽의 `yt-dlp 업데이트` 버튼으로 최신 버전으로 바꾸고 Node.js 22+ 또는 Deno 2.3+가 설치돼 있는지 확인한 뒤 다시 받으세요. 같은 안내가 앱 위쪽 도구 패널의 `yt-dlp 업데이트` 버튼 옆에도 표시됩니다.
- ffmpeg는 PATH 또는 `%APPDATA%\xGetSongs\bin`에서 찾으며, 따로 경로를 지정하는 설정은 아직 없습니다.
- 앱을 두 번 실행해도 두 번째는 첫 창을 앞으로 가져오고 바로 끝납니다. 같은 앱 데이터 폴더(`%APPDATA%\xGetSongs`)를 쓰는 다른 실행(개발용 점검 등)과는 동시에 실행하지 마세요: 서버가 시작할 때 임시 폴더(`work/`)를 비우므로 먼저 실행한 앱의 진행 중 항목이 실패할 수 있습니다.
- 화면 새로고침(F5, Ctrl+R)은 막혀 있습니다. 서버는 작업의 이벤트를 한 번만 내주므로 새로고침하면 돌고 있는 작업을 다시 따라갈 수 없기 때문입니다.
- 이벤트 연결이 끊기면 같은 작업에 다시 붙을 수 없고 취소만 됩니다.
- 요약의 "건너뜀" 개수에는 조회 단계에서 이미 사용할 수 없던 영상이 빠집니다(목록의 각 행에는 표시됩니다).
- ffmpeg가 없으면 다운로드를 시작하기 전에 첫 항목이 실패하며 작업이 중단됩니다. 도구 패널의 안내를 먼저 확인하세요.

## 주의

- 내려받은 콘텐츠의 저작권과 YouTube 서비스 약관은 사용자의 책임입니다. 본인이 사용할 목적으로만 쓰세요.
- 내장 서버는 `127.0.0.1`에만 열리며, 실행할 때마다 새로 만든 토큰이 있어야 접근할 수 있습니다.
