# xGetSongs Qt 판

C++20 / Qt 6 Widgets로 다시 쓰는 xGetSongs. 이 폴더가 제품 빌드이고, `qt/spike/`는 버려도 되는 스파이크다.

## 필요한 것

- Visual Studio 2022 (MSVC, 함께 오는 CMake와 Ninja)
- vcpkg (저장소 밖). 프리셋은 그 위치를 환경 변수 `VCPKG_ROOT`에서 읽는다. 이 PC에서는 `C:\dev\vcpkg`. 기준선 커밋 `4702e381dbbd9b54d3f7e1eb565cd8981c1814cd`(`qt/vcpkg.json`의 `builtin-baseline`)
- Qt 6.11.3 (vcpkg 포트 `qtbase`), 트리플렛 `x64-windows-static`(Qt와 CRT 정적 링크)
- 지원 Windows: Windows 10 이상 (`_WIN32_WINNT=0x0A00`)

## 공통 명령

저장소 루트에서 실행한다. vcpkg 의존성은 매니페스트 모드라 빌드 폴더의 `vcpkg_installed`(`build/qt/vcpkg_installed`)에 설치된다. 첫 명령은 그 호출에만 `VCPKG_ROOT`를 정한다(`&&` 앞에 공백을 두지 않는다. 두면 값 끝에 공백이 붙는다).

```
cmd /c "set VCPKG_ROOT=C:\dev\vcpkg&& call "C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Auxiliary\Build\vcvars64.bat" && cmake --preset qt-release -S qt && cmake --build build/qt"
ctest --test-dir build/qt --output-on-failure
pwsh qt/tools/differential/run.ps1 -Kinds <글자들> [-PerKind 10000] [-Seed 20261115] [-DebugTool]
```

세 번째는 대조 도구다(아래). 관문 점검(아래 "관문")은 이 명령들에 두 스크립트를 더한다. 실행 파일(테스트 포함)은 `build/qt/` 바로 아래에 생긴다(`CMAKE_RUNTIME_OUTPUT_DIRECTORY`).

### 디버그 빌드

프리셋 `qt-debug`는 `build/qt-debug`에 Debug(`/MTd`)로 빌드한다. Qt의 단언(`Q_ASSERT`)과 `QString`/`QList` 범위 검사가 켜져 있어서, 릴리스에서는 조용히 지나가는 범위 밖 접근이 테스트를 멈춘다. 의존성은 그 폴더의 `vcpkg_installed`에 바이너리 캐시에서 다시 설치된다. 관문에서 릴리스 테스트 다음에 돌린다.

```
cmd /c "set VCPKG_ROOT=C:\dev\vcpkg&& call "C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Auxiliary\Build\vcvars64.bat" && cmake --preset qt-debug -S qt && cmake --build build/qt-debug"
ctest --test-dir build/qt-debug --output-on-failure
```

대조 도구와 두 관문 스크립트는 `build/qt`(릴리스)의 실행 파일을 쓴다. 대조 도구에 `-DebugTool`을 주면 디버그 빌드의 `build/qt-debug/xgs-diff.exe`도 같은 사례에 답하게 해서 릴리스 답과 줄마다 같은지 본다(아래 "대조 도구").

### 실제 도구 통합 테스트

`tests/integration/`의 `tst_real_ffmpeg_tagging`(Kotlin `RealFfmpegTaggingIntegrationTest`, 8개), `tst_real_ytdlp`(Kotlin `RealYtDlpIntegrationTest`, 5개와 더한 2개), `tst_real_lrclib`(Kotlin `RealLrclibIntegrationTest`, 4개와 더한 2개)는 실제 ffmpeg·ffprobe·yt-dlp를 돌리고 실제 LRCLIB에 묻는다. 환경 변수 `XGS_INTEGRATION`이 `1`일 때만 돌고, 아니면 모든 시험이 건너뜀(`SKIP`)으로 끝나서 보통 `ctest`는 도구도 네트워크도 건드리지 않는다. ctest 레이블은 `integration`이다(`ctest -L integration`으로 이것만, `-LE integration`으로 이것을 빼고).

```
$env:XGS_INTEGRATION='1'; build/qt/tst_real_ffmpeg_tagging.exe -o "$env:TEMP\xgs-ffmpeg.txt,txt"; build/qt/tst_real_ytdlp.exe -o "$env:TEMP\xgs-ytdlp.txt,txt"; build/qt/tst_real_lrclib.exe -o "$env:TEMP\xgs-lrclib.txt,txt"; Remove-Item Env:XGS_INTEGRATION
```

- 도구는 Kotlin 통합 테스트와 같은 곳에서 찾는다: `ToolLocator`에 `%APPDATA%\xGetSongs\bin`(`APPDATA`가 없으면 `<사용자 폴더>\.xgetsongs\bin`)을 주고, 그다음 `PATH`. 그 폴더는 읽기만 하고 거기 있는 `yt-dlp.exe`·`ffmpeg.exe`를 실행할 뿐 아무것도 쓰거나 고치지 않는다(`yt-dlp -U`도 부르지 않는다). ffprobe는 찾은 ffmpeg 옆(`ffmpeg.exe` → `ffprobe.exe`)에 있어야 한다.
- 건너뛰는 조건은 Kotlin의 `assumeTrue`와 같고 문구도 같다: ffmpeg 쪽은 `ffmpeg and ffprobe must be installed`, yt-dlp 쪽은 `yt-dlp, ffmpeg and Node 22+/Deno 2.3+ must be installed`(js 런타임은 `ToolLocator`가 찾은 deno나 node; Kotlin처럼 버전은 보지 않는다).
- ffmpeg 쪽은 네트워크를 쓰지 않는다(무음 m4a와 빨간 그림을 ffmpeg로 만들어 태그를 쓰고 ffprobe로 읽는다).
- yt-dlp 쪽은 유튜브에 실제 요청을 보낸다: 재생목록 `PL2HEDIx6Li8jGsqCiXUq9fzCqpH99qqHV`의 목록(`--flat-playlist`), 영상 `kcx0a2OAhN0`·`7mDDM0eBWR0`·`jNQXAC9IVRw`(두 번)의 정보 파일과 썸네일(`--skip-download`, 오디오 없음). 한 번 돌리면 yt-dlp를 다섯 번 띄운다. 오디오를 내려받는 `writesTheInfoFileNextToTheM4aAndTheTestVideoHasNoAlbum`(19초 영상)은 `XGS_INTEGRATION_AUDIO=1`도 있어야 돌고, `downloadsAShortVideoAsM4aWithoutReencoding`은 내려받기·가사·태그를 잇는 내려받기 작업(Q2d)이 아직 없어서 늘 건너뛴다(LRCLIB 조회는 Q2c에서 이식했다).
- `tst_real_lrclib`는 실제 `https://lrclib.net`에 묻는다(한 번 돌리면 요청 15개 안팎, 최악은 30개 남짓). Kotlin처럼 서비스가 세 번(2초 간격) 답하지 않거나 5xx만 주면 실패가 아니라 건너뜀(`lrclib.net must answer`). 가사는 저작물이라 **가사 글자와 곡 이름 값은 찍지도 저장하지도 않는다**: 출력은 상태 코드, 키 이름과 값의 종류, 줄 수·글자 수뿐이고, 단언은 실패 메시지에도 가사가 실리지 않게 쓴다. 더한 두 시험: `theRealServiceIsReachedOverSchannelTls`(실제 TLS 연결로 상태 200~599)와 `downloadsTheRealYtDlpExecutable`(`XGS_INTEGRATION_DOWNLOAD=1`일 때만 `tools::YtDlpUrl`의 약 18MB를 받아 `MZ`로 시작하는지 본다; 디스크에 쓰지 않고 실행하지 않으며, 다른 때는 늘 건너뜀). 계획 검증에서는 `XGS_INTEGRATION_DOWNLOAD`와 `XGS_INTEGRATION_AUDIO`를 켜지 않는다.
- yt-dlp가 쓰는 것은 모두 한 `QTemporaryDir` 안에 남는다: 그 시험 클래스 동안 `XDG_CACHE_HOME`(yt-dlp의 캐시, 기본은 `%USERPROFILE%\.cache\yt-dlp`)과 `TEMP`·`TMP`(한 파일짜리 `yt-dlp.exe`가 풀리는 곳)를 그 안으로 돌리고, 시험마다의 임시 폴더도 그 안에 만든다. 끝나면 원래 값으로 되돌린다.
- 더한 두 시험: 공백·한글·`&`가 든 출력 폴더, 그리고 `%`가 든 출력 폴더. yt-dlp는 `-o` 값을 폴더까지 템플릿으로 읽어서 `%(id)s`는 영상 ID로, `%%`는 `%`로 바꾸고(홀로 선 `%`는 남는다) 다른 폴더에 조용히 쓴다(yt-dlp 2026.08.19에서 관찰). 그래서 `ytdlp::escapeOutputTemplateDirectory`(모든 `%`를 겹친다)를 더했고, `downloadCommand`는 Kotlin 그대로 두며 호출하는 쪽(Q2d)이 겹친 폴더를 넘긴다. 시험은 겹친 폴더로 그 폴더 자체에 파일이 생기는지 본다.

## 관문

Q1(`shared` 이식), Q2a(`engine`의 순수 로직), Q2b(프로세스·도구·조회·태그·출력 폴더), Q2c(HTTP·yt-dlp 내려받기·LRCLIB)의 관문은 설계 §4의 두 조건이다: 이식 대상 Kotlin 테스트가 같은 이름으로 모두 통과하고, 대조에서 불일치가 0이다. 대조는 모든 종류(Q1·Q2a·Q2b·Q2c의 것)를 돈다. Q2b부터는 두 `ctest` 다음에 위 "실제 도구 통합 테스트"의 명령을 릴리스 빌드로 한 번 돌린다(`XGS_INTEGRATION_AUDIO`와 `XGS_INTEGRATION_DOWNLOAD`는 켜지 않는다; `tst_real_lrclib`는 실제 lrclib.net에 묻으므로 사용자가 허락한 횟수만 돌린다). 우리 대상을 깨끗이 다시 빌드한 뒤(아래 "깨끗한 빌드", 릴리스와 디버그 둘 다) 저장소 루트에서 차례로 돌린다. 하나라도 실패하면 C++을 고치고 처음부터 다시 돌린다(Kotlin 코드, 기대값, 문턱, 생성기의 강도는 바꾸지 않는다).

```
ctest --test-dir build/qt --output-on-failure
ctest --test-dir build/qt-debug --output-on-failure
pwsh qt/tools/test-names.ps1
pwsh qt/tools/forbidden-calls.ps1
pwsh qt/tools/differential/run.ps1 -PerKind 10000 -Seed 20261115
pwsh qt/tools/differential/run.ps1 -PerKind 10000 -Seed 1
pwsh qt/tools/differential/run.ps1 -PerKind 10000 -Seed 987654321
pwsh qt/tools/differential/run.ps1 -PerKind 10000 -Seed 20261115 -DebugTool
pwsh qt/tools/differential/run.ps1 -PerKind 100000 -Seed <아무 값>
```

- `test-names.ps1`: `qt/tools/test-classes.json`에 적힌 Kotlin 테스트 클래스마다 `@Test` 함수 이름과 `build/qt/<exe>.exe -functions`의 이름을 비교한다. 이 파일은 배열이고 항목마다 `kotlin`(저장소 기준 Kotlin 테스트 파일), `exe`(Qt 테스트 실행 파일 이름), `added`(Kotlin에 없지만 일부러 더한 이름)를 둔다. 테스트 클래스를 이식하면 여기에 항목을 더한다. 빠진 이름이 있거나, 그 클래스의 `added` 밖의 이름이 더해졌거나, `added`의 이름이 그 실행 파일에 없거나, Kotlin 테스트 파일에서 이름이 하나도 안 나오면 종료 코드 1이다. 지금 `added`는 Q1의 세 이름(`extractOnOneMegabyteDescriptionFinishesQuickly`, `redactPathsWithFiveThousandPartsFinishesQuickly`, `leadingNonBmpLettersAreDroppedLikeEmoji`)과 Q2a의 세 이름 `readsATenMegabyteInfoFileQuickly`(10MB `info.json`), `downloadRejectsAVideoIdThatIsNotAPlainFileNamePart`(파일 이름으로 못 쓰는 영상 ID를 거절, 아래 종류 `K`), `sigmaFormsAreTheSameLetterInMatching`(가사 매칭의 시그마 결정, 아래 "끝 시그마 계약")다. Q2b에서는 `tst_system_process_runner`에 열네 이름(인자 그대로 전달, 표준 입력 닫기, 파이썬 인코딩 변수, 없는 실행 파일, 배치 파일 거절, 손자까지 죽이기와 그 대조 실행, 병렬 실행의 파이프, 시작 전 멈춤, 콘솔 창 없음, 줄 처리기가 던지면 프로세스를 죽이고 다시 던지기 `aThrowingHandlerKillsTheProcessAndRethrows`, 그리고 최종 리뷰 뒤에 더한 셋: 정상 종료 뒤 남은 손자도 죽이기 `aGrandchildLeftRunningAfterANormalExitIsKilled`(작성자 결정 5), 명령에 NUL이 있으면 시작하지 않기 `aNulInTheCommandIsAStartFailure`, Job 밖 프로세스가 파이프 끝을 쥐어도 멈춤이 돌아오기 `aStopReturnsWhenAProcessOutsideTheJobHoldsThePipe`)을 더했다. `tst_tool_manager`에는 취소 세 이름(`installIsCancelledWhenTheFetchIsCancelled`, `cancelledInstallLeavesNoTemporaryFile`, `updateIsCancelledWhenTheRunIsCancelled`: Kotlin이라면 코루틴이 취소될 곳에서 결과가 취소이고 `yt-dlp.new.exe`가 남지 않는다)과 `installReplacesAnEmptyDirectoryAtTheTarget`(대상 자리의 빈 폴더는 설치 파일로 바뀐다), `aRunThatFailsAfterItsStartIsNotACancel`(시작한 뒤 실행기가 놓친 실행 `RunStatus::Failed`는 시작 실패처럼, 취소가 아니다)을 더했다. `tst_ytdlp_resolver`에는 `aCancelledRunIsCancelledAndFetchesNothing`(실행이 취소되면 `resolve`는 취소, `fetch`는 없음), `aRunThatFailsAfterItsStartIsAFailureNotACancel`(같은 `Failed`는 실패), `aPlaylistOfExactly999IsNotTruncated`(정확히 999개는 자르지 않음), `resolvesAFiveThousandEntryPlaylistQuickly`(한 줄 수 MB의 5,000항목 재생목록, 릴리스 3초 안)를 더했다. `tst_m4a_tagger`에는 `aStartFailureOfFfmpegIsAFailureAndKeepsTheOriginal`(ffmpeg가 시작하지 못하면 실패, 원본 그대로, 임시 파일 없음)과 `aRunOfFfmpegThatFailsAfterItsStartIsAFailureAndKeepsTheOriginal`(같은 `Failed`도 실패), `tst_local_folder_sink`에는 `putWorksWhenTheTargetPathIsLongerThan260`(출력 폴더와 대상 경로가 260 단위를 넘음)과 `putFailsWhenTheFolderIsNotADirectory`(폴더가 디렉터리가 아니면 `put`은 실패, `exists`는 거짓)를 더했다. `tst_ytdlp_commands`에는 `escapeOutputTemplateDirectoryDoublesEveryPercentSign`, `tst_real_ytdlp`에는 `anOutputFolderWithSpacesKoreanAndAnAmpersandWorks`와 `aPercentSignInTheOutputFolderIsReportedNotSilentlyMisplaced`(위 "실제 도구 통합 테스트")를 더했다. Q2c에서는 두 테스트 클래스를 이식했다: `tst_fallback_lyrics_provider`(Kotlin `FallbackLyricsProviderTest`)에 `aStopRequestStopsAskingTheRemainingProviders`(멈춤이 요청되면 남은 공급자에게 묻지 않고 없음: Kotlin이라면 취소된 `find`가 던진다)를, `tst_lrclib_lyrics_provider`(Kotlin `LrclibLyricsProviderTest`, 루프백의 가짜 LRCLIB와 실제 `QtHttpClient`)에 `aCallWaitingForASlotReturnsWhenItIsCancelled`(자리를 기다리는 호출도 멈추면 요청 없이 돌아옴), `aCancelledCallDoesNotStartTheCoolDown`(멈춘 호출은 쉬는 시간을 시작하지 않음), `aNameLongerThanAThousandUnitsIsReadAsMissing`(1,000 단위 넘는 이름은 없음으로 읽음, 승인된 차이), `malformedUtf8InABodyIsReadLikeKotlinDoes`(본문의 잘못된 UTF-8은 Kotlin `String(bytes, UTF_8)`처럼 U+FFFD), `manyCallsCancelledAtOnceAllReturn`(한꺼번에 멈춘 열두 호출이 모두 3초 안에 돌아옴), `aRequestTimeoutOfZeroSendsNothing`(요청 시간 0이면 두 호출 모두 아무것도 보내지 않음. 공급자는 Kotlin처럼 쉬는 시간도 시작하지만 밖에서는 보이지 않는다, `FakeHttpClient`), `anInstrumentalFlagIsReadWhateverItsCase`(대조 `W lf`가 찾은 것: `instrumental`의 `TRUE`·`tRuE`·`falſe`도 불리언으로 읽음, `FakeHttpClient`)를 더했다. UTF-8이 아닌 바이트, BOM, 끝 줄바꿈 없음·`\r\n`, 문서 앞의 경고 줄, 빈 출력도 섞는다. stderr는 종류 `E`의 생성기다. 통계는 `rs`의 `OK` 40%·`ERR` 20%, 재생목록 실행(Kotlin 명령에 `--flat-playlist`) 30%·영상 실행(`--no-playlist`) 20%, 답에 쓸 수 없는 항목 10%, stdout을 실제로 읽은 사례(yt-dlp가 돌고 종료 코드 0) 가운데 `entries` 안에 글자 그대로의 `null` 항목이 있고 Kotlin이 받은 재생목록 5%, 형 어긋난 속성이 있고 Kotlin이 거절한 stdout 10%(통계용 C# 훑기가 찾은 것에서 Kotlin이 받은 것, 곧 훑기가 틀린 것을 뺀다; 뺀 수도 따로 보여 준다), 표준 JSON이 아닌 stdout 5%, `MAX_RANK`에서 잘린 답 1%, `fx`의 메타데이터·`NULL` 각 30%를 본다.

`xgs-diff arglists <count> <seed>`와 `Oracle.java argv <xgs-test-child 경로>`는 관문이 아닌 관찰 도구다: 오라클이 `ProcessBuilder`로 인자 목록을 `xgs-test-child argv`에 넘겨, 자식의 C 런타임이 받은 목록이 준 것과 다른 수를 센다(Q2b Task 2 Step 4).

**끝 시그마 계약**: `kt::lowercase`는 Kotlin과 같다. 단 대문자 시그마(`Σ`)가 `σ`가 될지 `ς`가 될지는 유니코드의 `Final_Sigma` 규칙(Unicode Standard 3.13, SpecialCasing.txt)을 근사한다. 앞뒤 글자가 Cased인지는 Qt의 대문자·소문자·제목 글자 범주로 정하고, 무시하는 문장부호(case-ignorable)는 `kt_text.cpp`에 적은 목록으로 정하므로 규칙 전체를 구현한 것은 아니다(Kotlin/JVM은 단어 경계로 정해 일부 문맥에서 다르다). Q1의 이식 코드에서 `lowercase()`의 결과는 정해진 ASCII·한글·CJK 집합(잡음 토큰, 가사 표지, 구간 접두어, 호스트 이름, 장치 이름)과 비교될 뿐이라 이 차이는 어떤 출력에도 드러나지 않는다(다음 단계의 `engine`은 사용자 글을 소문자로 바꿔 서로 비교하므로 그 전에 정해야 한다). 그래서 대조 종류 `S`의 `lower`는 입력에 `Σ`(U+03A3)가 있는 사례에서만 두 답의 `ς`(U+03C2)를 `σ`(U+03C3)로 접어 비교한다(`run.ps1`의 `$Folding`). 입력에 `Σ`가 없으면 `ς`도 그대로 비교한다.

가사 매칭(`core/lyrics/lyrics_matcher.*`)은 사용자 결정(2026-11-15)으로 Kotlin과 일부러 다르다: 정규화가 소문자로 바꾼 뒤 `ς`(U+03C2)를 `σ`(U+03C3)로 쓰므로 두 꼴이 같은 글자다(Kotlin은 다르게 본다). 그래서 위 근사는 매칭 결과에 드러나지 않고, 대조 종류 `I`의 사례에는 `Σσς`(와 NFKC로 그것이 되는 글자)가 없으며, 이 동작은 C++ 전용 테스트 `sigmaFormsAreTheSameLetterInMatching`이 정한다.

종류를 더하는 곳: 생성기(`gen.cpp`의 `registerGenerators()`에서 `registerKind`), C++ 답(`main.cpp`의 `registerAnswers()`에서 `registerAnswer`), Kotlin 답(`Oracle.java`의 `switch (part[0])`에 `case`), 통계 문턱(`run.ps1`의 `$Statistics`). 표 종류(`U`, `X`, `M`, `B`, `Z`)는 `$Statistics`에 `Table`(두 쪽이 찍는 표의 이름)을 둔다.

### `core/text/kt_tables.inc`

`pwsh qt/tools/differential/gen-tables.ps1`이 만든다(손으로 고치지 않는다). 내용은 JVM 21이 구현한 유니코드 판의 문자 데이터(Unicode Character Database)이고, JVM의 공개 API에 물어 얻는다. Qt 6.11.3의 유니코드 데이터와 JVM 21.0.9가 다른 단위 **48개**(isWhitespace 0, isLetter 16, isLetterOrDigit 16, uppercaseChar 35, lowercaseChar 9)는 JVM의 답을 표로 둔다. 그 밖에 유니코드 SpecialCasing 자료(JVM의 공개 API로 얻은 것)의 특수 대문자 102개(`ß`→`SS` 등)와 특수 소문자 1개(`İ`→`i̇`), BMP 밖 대소문자 대응 520개가 들어 있다. BMP 밖에서 `Character.isLetterOrDigit(int)`가 Qt의 범주(L*, Nd)와 다른 코드 포인트 **9,642개**(42개 범위, 종류 `B`의 예외; 대부분 Qt의 유니코드 17.0에만 있는 글자)는 JVM의 답을 범위로 둔다. NFKC(`Z`)의 예외는 **0개**다: `kt::nfkc`는 `QString::normalized`에 JVM 21의 유니코드 판(15.0, `QChar::Unicode_15_0`)을 주며, 그러면 15.0 뒤에 생긴 코드 포인트를 JVM이 미할당 코드 포인트를 다루듯 그대로 둔다(판을 주지 않으면 `Z` 40개, `H` 1만 건 중 1,396건이 다르다). `kt_text.cpp`는 이분 탐색하는 표마다 정렬돼 있는지 컴파일할 때 확인한다(`static_assert`). Qt나 사이드카 이미지의 JVM이 바뀌면 다시 만들고 `U`·`X`·`S`·`B`·`Z`·`H`를 돌린다. 이 자료의 고지는 저장소 루트의 `THIRD-PARTY-NOTICES.md`에 있다.
